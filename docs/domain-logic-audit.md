## A. 원본 코드가 SPEC보다 낡은 부분

원본을 그대로 Kotlin으로 옮기면 안 되는 자리다. 부록 D가 경고한 건 A1·A2뿐이고, **A3~A6은 어디에도
경고가 없다.**

| # | 항목 | 원본 `engine.js` / `courses.js` / `tourapi.js` | SPEC |
|---|---|---|---|
| A1 | 산책 블록 | D-1 20:00 · D-day 20:30 · D+N 08:00 — **3개 있음** | 전부 삭제 (§5.6) |
| A2 | 산책용 POI 적재 | 숙소 기준 `nature` 6건 별도 조회 (`pools.walk`·`sources.walk`) | 삭제. §6.3 `sources` 계약에서 `walk` 키도 빠진다 |
| A3 | `rule.walk` 용도 | 산책 블록 거리 라벨(`walkDesc`) | **S7→S8 연계 시 목표거리 기본값 `min(walk,5)km`** — 용도가 통째로 바뀜 |
| A4 | 블록 종류 | 없음 (`id·time·title·catKey·place·desc`) | `USER`/`RACE` + `systemManaged` 신설 (§5.6-7·§5.7) |
| A5 | `courseRegions()` | 시도명 배열만 반환 — 개수를 버린다 | "시도별 코스 수 내림차순" (§5.8). UI가 칩에 숫자를 표시해야 함 |
| A6 | `searchWalkSpots` limit | 기본값 **10** | **12**곳 (§4.11-7 · §5.9) |

**A3은 아직 어디에도 구현이 없다.** SPEC에 한 줄 있을 뿐이고, 원본에도 목업에도 없다. 목업의
`goCoursesFromHotel()` 은 출발지만 바꾸고 목표 거리는 건드리지 않는다.

### 그대로 옮겨도 되는 것 (원본 = SPEC 확인 완료)

카테고리 풀 결정 · POI 8건 · `pickTheme` 순서(`[...themes, tour, nature, cafe, history]`) ·
회복 배지 규칙 · `stdEvent`/`stdEventKm` 버킷(≥32/≥18/≥9) · 걷기 스팟 포함·제외 정규식 2개(SPEC
표와 문자 단위로 동일) · 원본 `buildRouteNear`에서 승계한 현재 `buildCuratedRouteNear` 왕복 알고리즘 · 분당 110m · shortfall −300m.

| # | 항목 | 목업 | SPEC |

| B3 | 회복 배지 | **항상** 표시 + 문구 하드코딩 | `noHard`(하프·풀)만. 5K·10K는 배지 없음 |
| B4 | 편집 모드의 대회 블록 | 교체 버튼만 숨김. **삭제·드래그는 열려 있음** | RACE는 모든 변경 거부, 그립·교체·삭제 **미노출** (§5.7) |

**B4는 버그다.** 편집 모드에서 "🏁 스타트" 블록의 ✕를 누르면 지워진다. 서버는 이 요청에
`409 SYSTEM_BLOCK_IMMUTABLE` 을 반환하기로 돼 있으므로, 이대로 포팅하면 누르면 에러가 나는
화면이 된다.

B1 때문에 캡처된 동선 결과 화면(`23-result`·`93-result-d1`·`94-result-dplus1`)은 전부 같은
가짜 데이터다. 보드에서 리뷰할 때 감안해야 한다.

## C. 데이터 — 두루누비에는 서울이 없다 (확정)

`durunubi_courses.json` 261코스를 실측하고, 두루누비 API를 직접 호출해 확인했다.

### C1. 261개는 코리아둘레길 전부다

```
서해랑길 94 + 남파랑길 85 + 해파랑길 45 + DMZ평화의길 37 = 261
```

API의 `routeList`(길 목록)를 부르면 **길이 딱 4개** 나온다 — 위 네 개가 전부다.
`crsKorNm` 으로 `서울둘레길`·`서울`·`한강`·`둘레길` 을 검색해도 **모두 0건**이다.
지자체 둘레길·서울둘레길은 두루누비에 없다.

즉 **두루누비 API로 서울 코스를 얻는 방법은 없다.** 덜 받아온 게 아니라 원래 없다.

### C2. 시도별 분포 (실측)

```
전남 71 · 강원 43 · 경남 41 · 충남 32 · 경기 20 · 경북 19
전북 14 · 인천  9 · 부산  6 · 울산  5 · 서울  1      (11개 시도, 제주 0)
```

서울 1건은 `DMZ 평화의 길 19-1코스(우회로)` 가 강동구에 걸친 것이다.

### C3. SPEC §4.11 프리셋 칩 5개를 `buildRouteNear(radiusKm=8)` 로 실측

| 프리셋 | 반경 8km 내 코스 | 가장 가까운 코스 |
|---|---|---|
| 부산 해운대 | 2 | 해파랑길 2코스 (32m) |
| 여수 | 6 | 남파랑길 55코스 (398m) |
| 인천 강화 | 2 | DMZ 평화의 길 1코스 (2.6km) |
| 강릉 | 1 | 해파랑길 39코스 (**4.7km** — 걸어서 한 시간) |
| **서울시청** | **0** | **없음** |

**서울 사용자는 두루누비 경로를 한 번도 못 본다.** 이 데이터 공백 자체는 변하지 않지만,
2026-08-19 개정 결정-42가 서버 품질 상한을 통과한 OSM·GraphHopper 도시 순환 경로 생성을 P0에 포함해 서비스 공백을 해소한다.

- 목표 거리·상승 `<50m/km` 큐레이션 경로가 있는 지역 — 검증된 두루누비·산림청 경로를 왕복으로 제공
- 적격 큐레이션 경로가 0건인 지역 — OSM `run` 프로파일로 거리·상승·차도·실제 회전 상한을 통과한 순환 경로 최대 1건 생성
- 적격 OSM 후보 0건 — 정상 결과로 카카오 걷기 스팟 점 목록만 제공
- GraphHopper 호출 실패 — 다른 항목이 있으면 부분 성공, 표시 항목도 없으면 Error

걷기 스팟은 더 이상 수도권의 유일한 기본 경험이 아니라 OSM 생성 경로와 함께 제공되는 장소 목록이자
라우팅 실패 fallback이다. OSM PoC의 수도권 20곳·1~21km·SRTM과 실제 회전 필터 검증 근거는 이슈 #33과 PR #32 `a4587ef`에 있다. 차도 상한은 path detail 포인트 수가 아닌 폴리라인 실거리 가중 방식으로 재검증해야 한다.

### C4. ⚠ API에서 다시 받으면 코스가 반토막 난다

두루누비 API가 지금 주는 코스는 **144개**뿐이다. 우리 파일 261개와 비교하면,

- 겹침 **142** · API에만 있음 **2** · **우리에만 있음 119**

즉 예전에 받아둔 119개가 API에서 사라졌다. **"최신화"한다고 API 응답으로 덮어쓰면 261 → 144로
줄어든다.**

SPEC §8.4는 이미 이걸 막아 두었다. 코스를 `API_GPX`(142) / `GPX_ONLY`(119) / `API_ONLY`(경로 없음)
로 나누고 **앞의 둘만 서비스**한다. 이 설계를 지켜야 하며, 나중에 "API가 최신이니 API만 쓰자"고
단순화하면 119개를 잃는다.
