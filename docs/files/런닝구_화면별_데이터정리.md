# 런닝구 — 화면별 데이터 정리 v2 (설계 결정 반영)

> **v1 → v2 변경 요약**
> ① 데이터 소스 원칙 확정: 대회 = 크롤링→DB, 나머지 = 외부 API 실시간 호출 (공모전 규정)
> ② Festival / Place / Accommodation / RunningCourse 마스터 테이블 삭제 → **스냅샷 방식**으로 전환
> ③ 동선 3단 구조 + 편집 API 방식 확정 (하루 단위 PUT 전체 교체)
> ④ GPS 궤적 = polyline 압축 저장(1:1 분리 테이블) 확정
> ⑤ 페이징(대회 목록 커서) · 날짜별 집계 API 분리 확정

표기 규칙: **표시** = 화면에 보이는 값 / **숨은 값** = 안 보이지만 서버가 줘야 하는 값 / **액션** = 사용자가 서버에 보내는 값 / **상태** = 목업에 정의된 로딩·빈·에러 화면

---

## 0. 데이터 소스 원칙 (공모전 규정)

규정: **외부 API를 실시간 호출해서 사용해야 하며, API 데이터를 DB에 저장해두고 쓰는 방식은 인정되지 않음.**

| 데이터 | 소스 | 방식 |
|---|---|---|
| 대회 | 마라톤 온라인 · 마라톤GO **크롤링** | 배치(1일 1회, 새벽) → DB upsert. 공식 API 부재로 예외 (주최측 확인 예정) |
| 대회장 좌표 | 카카오 로컬 API (지오코딩) | 크롤링 배치 안에서 장소명→좌표 1회 변환 후 저장 |
| 축제 | 한국관광공사 TourAPI | **실시간 프록시** (행사정보조회 + 위치기반조회) |
| 관광지·맛집·카페 등 POI | 한국관광공사 TourAPI | **실시간 프록시** (위치기반/키워드 조회) |
| 숙소 | 한국관광공사 TourAPI (숙박, contentTypeId=32) | **실시간 프록시** |
| 러닝코스 | 두루누비 API (제공 여부 확인 중) | **실시간 프록시** 목표. 미제공 시 대안 결정 필요 |
| 계정·찜·동선·러닝 기록 | 자체 생성 데이터 | DB |

**저장 원칙**: 외부 API 데이터는 저장하지 않는다. 예외는 두 가지뿐.
1. **대회** — 공식 API가 없어 크롤링→DB (규정 예외로 주최측 확인)
2. **사용자가 "저장"한 동선·코스 내부의 장소 정보** — 마스터 테이블이 아닌, 선택 시점의 이름·주소·좌표 **스냅샷 복사본** (사용자 생성 데이터의 일부로 해석)

> 실시간 프록시 = 클라이언트 요청 → 우리 서버가 외부 API 호출 → 가공 → 응답 (DB 저장 없음)

## 공통 (모든 화면)

| 항목 | 내용 |
|---|---|
| 하단 탭 | 홈 / 캘린더 / 러닝코스 / 보관함 (4개 화면에서만 노출) |
| 스낵바 | 서버 응답 후 토스트 문구 ("찜했어요", "보관함에 저장했어요" 등) |
| 게스트 모드 | 조회는 전부 공개, 찜·저장·기록만 인증. 인증 필요 API가 **401** 반환 → 클라이언트가 "로그인이 필요해요" 모달 |
| 뒤로가기 | `backTo`는 클라이언트 상태, 서버 불필요 |

**숨은 값 (전역)**: 사용자 id, accessToken, 게스트 여부

## 1. 인증

### 1-1. 로그인
- **표시**: 이메일, 비밀번호 입력, 에러 문구
- **액션**: `email`, `password` → 응답 `accessToken`, `refreshToken`, `user{id, nickname, email}`
- **상태**: `loginError` — 아이디/비밀번호 불일치
- **분기**: 게스트로 시작하기 (토큰 없이 홈 진입)

### 1-2. 회원가입 (4단계)
| 단계 | 데이터 |
|---|---|
| 1. 동의 | `tos`(필수), `privacy`(필수), `mkt`(선택) — 필수 2개 미동의 시 다음 버튼 비활성 |
| 2. 정보 입력 | 이메일, 비밀번호, 비밀번호 확인, 닉네임 |
| 3. 이메일 인증 | 6자리 숫자 코드, 재발송 쿨다운 60초 |
| 4. 완료 | 없음 (시작하기 → 홈) |

- **액션**: 회원가입 요청, 인증코드 발송, 인증코드 검증
- **숨은 값**: 코드 만료시각(서버 기준), 이메일 중복 여부

### 1-3. 비밀번호 찾기 / 재설정
- **액션**: 재설정 메일 발송, `resetToken` + 새 비밀번호로 변경
- **숨은 값**: `resetToken`(링크 포함), 토큰 유효시간

## 2. 홈

- **표시**
  - 검색창 (대회명/장소/지역 통합, 엔터 시 캘린더로 이동하며 검색어 전달)
  - 퀵메뉴 4개: 달력 / 지도 / 코스 / 관광 (화면 이동만)
  - **마감 임박 대회** — 접수중만, `apply_end asc` 상위 4개 (목업 "접수 마감 순")
  - **축제·지역 관광 추천** — 축제명, 기간, 지역, 썸네일, 진행중 배지, 출처
- **숨은 값**: 대회 id, 축제 API의 contentId, 이미지 URL, 조회 기준 월
- **상태**: 축제 로딩 / 축제 없음 (`festLoading`, `festEmpty`)

> ✅ **확정**: 축제는 TourAPI **실시간 호출** (행사정보조회, 월 기준). `festLoading`/`festEmpty`가 곧 외부 API 지연·실패·빈 응답의 UX 매핑. 대회 리스트는 자체 DB 조회.

## 3. 캘린더 (대회 목록)

리스트 뷰 / 월간 뷰 세그먼트 토글.

### 리스트 뷰 — 대회 카드
| 표시 필드 | 예시 | 비고 |
|---|---|---|
| 월/일/요일 | `AUG` `22` `토` | contest_date에서 파생 |
| 대회명 | 2026 세종 호수공원 마라톤 | |
| 지역 · 장소 | 세종 · 세종중앙공원 | |
| 종목 태그 | 풀 / 하프 / 10K | CONTEST_EVENT 조인, 첫 태그 강조 |
| 종목 미표기 배지 | | 종목 정보 없는 대회 |
| 접수 상태 | `접수중 · ~08.10` / `접수전` / `마감` | status + apply_end 조합 |
| 출처 | 마라톤GO · 확인 07.15 | source + checked_at |
| 찜 하트 | on/off | 로그인 사용자별 |

- **숨은 값**: 대회 id, `contest_date >= today` 조건, 찜 여부, **커서(마지막 항목의 date+id)**
- **필터 시트**: 검색어 `q`(이름+장소+지역 부분일치), 종목 `events[]`(OR), `openOnly`, 지역 `regions[]`(17개 다중), 적용 개수 배지, draft→완료 시 적용
- **상태**: 조건에 맞는 대회 없음 (필터 초기화 버튼)

> ✅ **확정**: 대회 목록은 **커서 페이징** — `WHERE (contest_date, id) > (:d, :id) ORDER BY contest_date, id LIMIT 20`. 보조 정렬 id 필수(동일 날짜 순서 안정화).

### 월간 뷰
- **표시**: 년/월, 날짜 셀, 대회 있는 날 점, 2개 이상이면 숫자 배지, 오늘 테두리, 선택 날짜의 대회 목록
- **상태**: 이 날엔 / 이 달엔 대회가 없어요

> ✅ **확정**: 날짜별 개수는 별도 집계 API `GET /api/contests/daily-counts?year=&month=` (GROUP BY). 목록 API와 **필터 Predicate 공유** (QueryDSL) — 점 표시와 목록 불일치 방지.

## 4. 대회 상세

- **표시**: 지역·마라톤(eyebrow), 대회명, D-day, 날짜·요일, `출발 08:00 · 세종중앙공원`, 접수 상태 배지
- **정보 행**: 종목, 접수 기간, 주최, 출처
- **버튼**: 공식 페이지(외부 URL), 찜, 이 대회로 동선 만들기
- **인근 축제**: 축제명, 기간, **대회장 기준 거리(0.8km)**, 썸네일, 출처
- **숨은 값**: 대회 id, official_url, **대회장 좌표(lat/lng — 배치 지오코딩으로 확보)**
- **상태**: 인근 축제 로딩 / 없음

> ✅ **확정**: 인근 축제 = TourAPI **위치기반조회 실시간 호출** (대회장 좌표 + 반경, contentTypeId=15). 거리는 응답 좌표로 계산.
> ⚠️ 접수 시작일(`apply_start`)·주최(`host`)는 크롤링 소스에서 확보 가능한지 확인 필요 → 남은 항목.

## 5. 동선 위저드 (3단계)

### W1 — 기간 선택
- **표시**: 패턴 5개(전날부터/대회+다음날/전후로/당일치기/직접 선택), 달력(대회일 강조), 기간 라벨
- **액션 값**: `pattern`, `startDate`, `endDate`

### W2 — 종목 & 취향
- **표시**: 종목 세그먼트(5K/10K/하프/풀), 종목별 예상 피로도, 취향 칩 6개, 회복 일정 안내
- **액션 값**: `event`, `prefs[]`
- **규칙(서버 상수)**: 피로도 매핑 `5K 거의 정상 / 10K 낮은 피로 / 하프 중등도 / 풀 고강도 회복 필요`

### W3 — 숙소 선택
- **표시**: 숙소 검색창, "대회장 주변 숙소" + LIVE 배지, 숙소명 + `어진동 · 대회장 1.2km`
- **상태**: 숙소 로딩 / 없음

> ✅ **확정**: 숙소 = TourAPI **실시간 호출** (위치기반, 대회장 좌표, contentTypeId=32 / 키워드 검색 병행). LIVE 배지가 실시간 의도의 근거.
> 동선 생성 액션 값: `contestId`, `startDate`, `endDate`, `event`, `prefs[]`, **`hotel{name, lat, lng}` 스냅샷** (hotelId 아님 — 숙소 마스터 테이블 없음)

## 6. 동선 결과

- **표시**
  - 지도: 경로 폴리라인 + 번호 핀, 일자별 색상(회복일 오렌지)
  - 헤더: `세종 2박 3일`, 총 장소 수, 공유
  - 일자 탭: `D-1 · 08.21 금` / `D-DAY` / `D+1`, 회복일 메모
  - **일정 블록**: 순번, 시간, 제목, 카테고리 태그, 장소명, 설명 / 대회 블록 특별 표시 / 숙소 블록에 "러닝코스에서 보기 →"
- **편집 모드**: 드래그 순서 변경, 장소 교체, 삭제, 추가 / 교체·추가 시트: 카테고리 칩 7종 + 인근 장소(실시간 API, LIVE 배지)
- **상태**: 동선이 아직 없어요 (다시 추천받기)

> ✅ **확정 설계** — `ITINERARY(1) → ITINERARY_DAY(N) → ITINERARY_BLOCK(N)`
> - 블록의 장소는 FK가 아닌 **스냅샷 컬럼**(place_name, address, lat, lng) — 장소 마스터 없음
> - **생성 API는 무상태**(규칙 엔진이 DTO만 반환, DB 기록 없음) / "이 동선 저장하기"가 트리 전체를 POST 1회 (cascade)
> - 저장 후 편집만 세분화 API: 순서 = `PUT /days/{dayId}/blocks/order` + `blockIds[]` → 집합 일치 검증 후 order_no 1..N 재부여 (**멱등**)
> - `race=true` 블록 교체 금지는 **서버가 강제** (PATCH 시 400) — 클라이언트 검증 신뢰 금지
> - 삭제 후 재번호 불필요 (order_no 구멍은 정렬에 무해)
> - 조회: days+blocks 동시 fetch join 금지 (MultipleBagFetchException) → `hibernate.default_batch_fetch_size=100` 배치 로딩
> - 생성 규칙 파이프라인: 날짜 골격 → 고정 블록(대회·체크인/아웃) → 종목→피로도 → 회복일 규칙 → 슬롯 채우기(숙소 좌표 반경 실시간 API × 취향 교집합, 거리순)

## 7. 러닝코스

### 내 주변
- **표시**: 내 위치 버튼, 출발지 검색, 프리셋 칩, 목표 거리 슬라이더 1~21km, 추천 코스(코스명/위치+진입점 거리/스펙), 짧은 코스 경고, 다른 코스 3개, 걷기 좋은 곳(지도 핀 연동)
- **액션 값**: `lat`,`lng` 또는 `startQuery`, `targetDistanceKm`
- **상태**: 위치 확인 중 / 출발지 미지정 / 결과 없음 / 코스 없이 장소만
- **버튼**: 코스 저장, 이 코스 뛰기

### 지역별
- **표시**: 지역 칩 + 개수, `전국 코스 261 · 두루누비 걷기길`, 코스 목록
- **상태**: 해당 지역 코스 없음

> ✅ **확정 방향**: 코스 = **두루누비 API 실시간 호출** 목표 (공공데이터포털 제공 여부 확인 중 — 남은 항목). "걷기 좋은 곳"은 TourAPI 위치기반.
> 코스 저장 시 SAVED_COURSE에 **스냅샷** 저장 (이름·지역·거리·난이도·진입점 좌표·경로 polyline) — 코스 상세의 점선 렌더링용.

## 8. GPS 기록 / 러닝 요약

- **기록 중 표시**: 경과 시간, 거리, 평균 페이스, 종료
- **요약 표시**: 날짜, 거리(`5.21 km`), 시간(`32:10`), 평균 페이스(`6'11"/km`)
- **액션**: 기록 저장(요약값 + 궤적 좌표 배열) / 삭제

> ✅ **확정**: RUN_RECORD(요약) + RUN_TRACK(**1:1 분리**, polyline 인코딩 문자열) — 목록 조회가 LOB를 안 건드리게 분리.
> 기록 시 **5m 이상 이동 시에만 좌표 추가** 필터 (노이즈·용량 절감). 지도 실선은 디코딩해 렌더링 (나이키런 방식과 동일 원리).
> 구간 페이스 분석 기능이 생기면 그때 포인트 테이블로 확장.

| 엔티티 | 컬럼 후보 | 비고 |
|---|---|---|
| USER | id, email, password, nickname, email_verified, created_at | |
| USER_AGREEMENT | user_id, tos, privacy, marketing, agreed_at | |
| EMAIL_VERIFICATION | email, code, expires_at, verified | Redis 대체 검토(남은 결정) |
| CONTEST | id, source, external_id, name, region, place, lat, lng, contest_date, start_time, status, apply_start?, apply_end, host?, official_url, checked_at | **(source, external_id) 유니크** = upsert 키. 좌표는 배치 지오코딩 |

| ITINERARY | id, user_id, contest_id, title, start_date, end_date, hotel_name, hotel_lat, hotel_lng, created_at | 숙소 스냅샷 |
| ITINERARY_DAY | id, itinerary_id, day_index, day_date, recovery, note | |

## 실시간 API 호출 지점 정리

| 화면 | 호출 | 기준점 |
|---|---|---|
| 홈 축제 리스트 | TourAPI 행사정보조회 (월) | 조회 월 |
| 대회 상세 인근 축제 | TourAPI 위치기반 (축제) | 대회장 좌표 + 반경 |
| 위저드 W3 숙소 | TourAPI 위치기반 (숙박) + 키워드 | 대회장 좌표 |
| 동선 생성 슬롯 채우기 | TourAPI 위치기반 (취향 카테고리) | 숙소 좌표 + 반경 |
| 장소 교체/추가 시트 | TourAPI 위치기반 (카테고리) | 현재 블록·숙소 좌표 |
| 러닝코스 내 주변/지역별 | 두루누비 API (확인 중) | 출발지 좌표 / 지역 |
| 지오코딩 (배치 내부) | 카카오 로컬 | 크롤링 장소명 |

**공통 방어**: 타임아웃 2~3초 → 실패 시 로딩/빈 상태 UI로 매핑 (목업의 festLoading/festEmpty), 쿼터 모니터링(개발키 일 1,000건 수준), 주최 허용 시 5분 단기 캐시.

## 확정된 설계 결정 (근거 요약)

1. **소스 분리** — 대회만 크롤링→DB(공식 API 부재), 나머지 전부 실시간 API (공모전 규정)
2. **동선 생성 = 규칙 기반 절차** — 조합 열거가 아니라 생성 파이프라인 코드화. 슬롯 채우기가 실시간 API를 사용해 규정의 핵심 기능화
3. **좌표 = DECIMAL 일반 컬럼** — 현재 규모에서 공간 인덱스는 과설계. 바운딩박스 + 하버사인으로 충분
4. **궤적 = polyline 압축 + 1:1 분리** — 접근 패턴이 "통째로 읽어 그리기"뿐이라 행 단위 정규화 이득 없음
5. **게스트 = 목업 그대로** — 조회 공개 / 쓰기 401. 생성(무상태)·저장(영속) API 분리로 고아 데이터 방지
6. **날짜별 개수 = 집계 API 분리** — 페이징과 클라이언트 집계는 양립 불가. 목록과 필터 조건 공유
7. **페이징 = 대회 목록만 커서, 나머지 Pageable** — 배치 삽입이 실제 일어나는 무한스크롤 목록에만 커서 가치가 있음
8. **동선 편집 = 하루 단위 PUT 전체 교체** — 멱등·검증 단순. 단건 이동/LexoRank는 이 규모에 과설계 (면접용 확장 멘트로만)
