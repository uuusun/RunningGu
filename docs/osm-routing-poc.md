## 1. 왜 했나

S8 러닝코스는 대회와 무관하게 **동네·여행지에서 자유롭게 뛸 코스를 추천**하는 기능이다.
그런데 현재 데이터로는 도시에서 코스가 나오지 않는다.

두루누비(코리아둘레길 261코스)는 해안선과 DMZ 를 따라간다. 마라톤 대회도 러너도 도시에 있는데
코스는 바닷가에 있다. 산림청 등산로 663코스를 더해 926코스로 늘렸지만 대부분 등산로였다.

| 지점 | 두루누비만 | +산림청 | 그중 완만한 것 |
|---|---|---|---|
| 서울시청 | 0 | 24 | 3 |
| 여의도 | 0 | 13 | 2 |
| 수원 | 0 | **0** | 0 |
| 성남 | 0 | **0** | 0 |
| 청주 | 0 | **0** | 0 |
| 대전 유성 | 0 | **0** | 0 |

산이 있는 도시만 채워졌다. 평지 도시는 그대로 0건이다. 도시에서 뛸 곳은 하천변·공원·산책로인데
두루누비에도 산림청에도 없다.

## 2. 무엇을 검증했나

OpenStreetMap 의 보행로·자전거도로를 GraphHopper 로 라우팅해 **코스를 생성**할 수 있는지 봤다.
OSM 은 완성된 코스가 아니라 길 조각의 그래프이므로, 출발점에서 목표 거리만큼 도는 순환 경로를
만들어내야 한다.

## 3. 결과

### 3-1. 수도권 20곳 전부 생성됨

5km 순환 코스 기준 **20/20 성공**. 두루누비+산림청으로 0건이던 지점들이다.

```
서울 여의도 · 강남역 · 잠실 · 상암 · 청량리 · 목동 · 노원 · 강서 · 관악
고양 일산 · 성남 분당 · 수원 영통 · 용인 기흥 · 부천 중동 · 안양 평촌
인천 송도 · 의정부 · 광명 · 김포 장기 · 남양주 다산
```

### 3-2. 기본 프로파일은 큰 도로를 쓴다 — 프로파일을 따로 만들어야 한다

GraphHopper 기본 `foot` 은 "보행자가 A→B 가는 최적 경로"를 찾는다. 러닝에 좋은 길을 찾는 게
아니라서 큰 도로 보도를 그대로 쓴다.

러닝 친화 가중치(`run` 프로파일)를 넣자 차도 비율이 이렇게 바뀌었다.

| 지점 | `foot` 차도 | `run` 차도 |
|---|---|---|
| 서울 여의도 | **31%** | **1%** |
| 서울 잠실 | 28% | 4% |
| 인천 송도 | 37% | 19% |
| 수원 영통 | 19% | 9% |
| 성남 분당 | 8% | 0% |

여의도 5km 코스가 보행로·자전거도로 **87%**, 차도 **1%** 로 나온다. 가중치는
[`scripts/osm/graphhopper.yml`](../scripts/osm/graphhopper.yml) 에 있다.

### 3-3. SPEC 의 1~21km 슬라이더 범위를 모두 만족한다

여의도 기준. 좋은길·차도·계단은 **폴리라인 실거리 가중**, 회전은 **실제 회전 신호만** 센 값이다.

| 목표 | 실제 | 좋은길 | 차도 | 계단 | 회전/km | 상승 |
|---|---|---|---|---|---|---|
| 5km | 5.21km | 87% | 1% | 0.00% | 5.4 | 113m |
| 10km | 9.10km | 92% | 0% | 0.23% | 3.0 | 119m |
| 15km | 13.86km | 58% | 0% | 0.19% | 3.2 | 188m |
| 21km | 22.34km | 61% | 0% | 0.00% | 1.7 | 353m |

`round_trip` 은 목표 거리를 정확히 맞추지 않고 1.1~1.5배로 낸다. **목표의 78% 로 요청**한 뒤
여러 seed 중 가장 가까운 것을 고르면 범위 안으로 들어온다. 다만 **정확히 맞지는 않는다.**

```
목표  5km → 오차  +211m
목표 10km → 오차  -895m
목표 15km → 오차 -1137m
목표 21km → 오차 +1338m
```

초판에는 오차가 +17m·+417m·-103m 로 적혀 있었으나, 계단 페널티(`b8b4c0e`)로 프로파일이 바뀌면서
후보 경로 자체가 달라졌다. **한 지점의 값이라 편차가 크다** — 수도권 20곳으로 재면 5km 중앙 174m,
10km 중앙 545m 다. 거리 정확도는 seed 수를 늘리거나 후보군을 넓혀야 좋아진다.

### 3-4. 고도는 SRTM 으로 채워진다

OSM way 1,243개를 확인한 결과 `ele` 태그가 **0개**다. OSM 자체에는 고도가 없다.
GraphHopper 설정 한 줄(`graph.elevation.provider: srtm`)로 위성 고도 타일이 자동으로 붙는다.

이 값이 있어야 `build_courses.py` 와 **같은 기준(m/km)** 으로 난이도를 매길 수 있다.

```
인천 송도   0 m/km   완전 평지(매립지)
부천 중동  10 m/km
서울 잠실  11 m/km   한강변
서울 관악  38 m/km   산을 끼고 도는 코스
수원 영통  40 m/km
```

### 3-5. 성능

```

재기동        30초 (캐시 재사용)
경로 1건      36ms (중앙값 · HTTP+파싱 포함 end-to-end)
seed 16개     0.52초
디스크        그래프 캐시 514MB + SRTM 44MB
```

## 4. 한계

- **짧은 거리는 방향 전환이 잦다.** 수도권 20곳에서 가장 적게 꺾는 후보를 봐도 5km 는
  **km 당 중앙 4.0회 · 최대 5.5회** 다. 차도를 피하려 골목·산책로를 이리저리 돌기 때문이다.
  거리가 길수록 나아진다 — 10km 중앙 3.3회, 21km 중앙 2.4회(최대 3.0회).
  (초판의 "5km 에 44회" 는 직진·출발·도착·길이름 변경 안내까지 센 값이라 과장이었다. `a4587ef` 참조.)
- **계단은 거의 섞이지 않는다.** 계단 가중치를 차도만큼 깎은 뒤(`b8b4c0e`) 상한 통과 후보의
  **70% 가 계단 0%**, 최대 0.95% 다. 별도 상한이 필요 없다.
- **긴 거리는 의도치 않게 산을 탈 수 있다.** 성남 분당 21km 에서 상승 1544m(70 m/km)가 나왔다.
  목표 거리를 채우려 주변 산으로 올라간 것이다. → **결정-42 개정에서 서버가 `HARD`(≥50m/km)를
  자동 추천에서 제외하는 것으로 해결했다.** 사용자에게 난이도를 고르게 하지는 않는다.
- **지역별 편차가 있다.** 자체 구현 PoC 에서는 청주가 실패했으나 GraphHopper 로는 성공했다.
  다만 OSM 매핑 밀도는 지역마다 다르므로 지방 소도시는 별도 확인이 필요하다.
- **주택가 골목이 섞인다.** 차도도 아니고 보행로도 아닌 `residential`·`service` 구간이
  수도권 5km 경로에서 중앙 15% 나온다. 서울 강서는 73%, 남양주 다산은 57% 로 사실상 골목만 돈다.
  후보 16개가 전부 그러므로 상한으로 거를 수 없다 — 상한을 걸면 경로가 사라진다(골목 ≤20% 는
  40건 중 32건만 남는다). 거르는 문제가 아니라 **고르는 문제**다.

## 5. 라이선스

ODbL. 공공누리 4유형(변경금지)인 서울둘레길과 달리 **가공에 제약이 없다.**

| | 서울둘레길(공공누리 4유형) | OSM(ODbL) |
|---|---|---|
| 출처표시 | 필요 | 필요 — `© OpenStreetMap contributors` |
| 상업적 이용 | 금지 | 허용 |
| 변경·가공 | **금지** | **허용** |
| 추가 조건 | — | 파생 **데이터베이스 배포 시** 동일 라이선스 |

share-alike 는 데이터베이스를 배포할 때 발동한다. **서버에서 경로를 계산해 결과만 응답하는
구조**는 Produced Work 이므로 해당하지 않는다. 앱에 OSM 파생 데이터를 번들하면 회색지대다.

## 6. 결론과 남은 결정

**도시 러닝코스는 OSM 으로 해결된다.** 경로가 나오는 정도가 아니라 차도를 피한 쓸 만한 코스가
나오고, 고도·난이도까지 기존 체계와 같은 기준으로 붙는다.

작업 규모는 라우팅 엔진을 새로 만드는 게 아니라 GraphHopper 를 붙이는 것이므로, 서버 통합 +
이상치 필터 + API 계약 정도다.

### 결정된 것 (SPEC 결정-42 · 2026-08-18 확정, 08-19 개정)

1. **도입 여부와 시점** → **P0**. AP-25 로 백로그에 올랐다
2. **배포 구조** → Spring Boot 와 **분리된 서버 내부 프로세스**. 그래프·SRTM 캐시는 배포 단계에서
   만들어 영속 볼륨에 둔다
3. **큐레이션 우선순위** → 큐레이션이 먼저다. 목표 거리에 맞고 `HARD` 가 아닌 큐레이션 경로가
   **0건일 때만** OSM 을 생성한다
4. **난이도 선택 기능** → **넣지 않는다.** 사용자 칩과 종목별 기본값을 모두 빼고, 서버가 품질
   상한으로 나쁜 경로를 거른다. 난이도(`EASY`/`NORMAL`)는 결과에 붙는 **표시용**이다

   `EASY` 를 기본값으로 두고 필터로 쓰면 수도권 커버리지가 60건 중 43건으로 떨어졌다.
   `HARD` 요청은 12건뿐이었다. 난이도를 안 보면 60/60 이다

### 확정된 품질 상한

거리 75~125% · 상승 `<50m/km` · 실거리 가중 차도 `≤10%` · 실제 회전 `≤6회/km` 를 **모두**
통과한 후보만 쓰고 상한을 완화하지 않는다. 이 조건으로 수도권 20곳 × 5·10·21km 중 **59/60** 에서
경로가 나온다(광명 5km 만 0건).

## 8. 후속 검증 — 골목 회피와 하천 유도 (2026-08-19)

4장의 "주택가 골목이 섞인다" 를 어떻게 할지 확인한 결과다. 재현은
`python scripts/osm/roundtrip.py --preset water --waterways data/waterways.json`.

### 8-1. 상한으로는 못 거른다

골목 비율에 상한을 걸면 커버리지가 무너진다. 난이도 때와 같은 함정이다.

| 상한 | 경로가 남는 지점·거리 |
|---|---|
| 없음 | 39/40 |
| 골목 ≤40% | 37/40 |
| 골목 ≤30% | 36/40 |
| 골목 ≤20% | **32/40** |

원인은 분명하다. **골목이 심한 곳은 후보 16개가 전부 그렇다.** 서울 강서 5km 는 6개 중
가장 나은 것도 골목 40%, 관악은 4개 중 51% 다. 동네에 보행로가 없는 것이라 상한을 걸면
더 나은 코스가 나오는 게 아니라 아무것도 안 나온다. **거르는 문제가 아니라 고르는 문제다.**

### 8-2. 후보를 여러 벌 만들어 고른다

| 후보 | 만드는 법 | 새로 필요한 것 |
|---|---|---|
| 동네 | 지금 그대로 | — |
| 골목 회피 | 요청에 `RESIDENTIAL`·`SERVICE` `×0.3` 한 줄 | **없음** |
| 하천 | 물길 버퍼 폴리곤 밖 `×0.4` (`custom_model.areas`) | 물길 인덱스 |
| 하천 진입 | 물길이 멀면 강변 진입점에서 시작 | 물길 인덱스 |

하천 버퍼는 물길 종류·규모별로 다르다 — 본류(15km 이상) 400m · 지천 200m · 운하 120m ·
실개천 60m. 한강처럼 폭이 넓은 강은 중심선에서 60m 만 두르면 물 위만 덮고 둔치 산책로가
버퍼 밖으로 빠진다(실측에서 목동·잠실이 이것 때문에 0% 였다).

### 8-3. 전국 물길 인덱스

`scripts/osm/build_waterways.py` 가 PBF 에서 한 번 뽑는다. 배포 단계 산출물이다.

```
물길      32,628 개 중 16,736 개 채택 (300m 이상 · river 1,980 · stream 14,596 · canal 160)
좌표      461,127 개 (50m 간격)      총 길이 44,442 km
격자      46,501 칸 (0.01도 ≈ 1.1km)
파일      10.8 MB                    빌드 18~70초
조회      1.5ms / 지점 (격자)
```

Overpass 로 받은 20곳과 대조해 같은 물길·거리가 나오는 것을 확인했다. 목동 안양천 444m,
노원 중랑천 244m, 청량리 청계천 1,010m 로 일치한다.

1. **계약의 커버리지는 수도권 기준이다.** 확정된 59/60 은 수도권 20곳만 잰 값이고,
   지방 10곳을 넣으면 **15/20** 이다. 강릉 교동 5km 는 어떤 방식으로도 안 나온다.
2. **지방이 훨씬 나쁘다.** 골목이 수도권 15% 대 지방 33% 다.
3. **골목 회피는 수도권에서만 듣는다.** 지방은 B 가 A 와 같다 — 골목 회피 후보가
   상한을 통과하지 못하거나 계약 규칙(거리 우선)에서 밀린다.
4. **선택 규칙이 결과를 가른다.** 같은 후보를 놓고도 계약 규칙으로 고르면 거리만
   좋아지고(318→115m) 품질은 안 오른다. 점수로 고르면 품질 84→90, 골목 18.6→7.0% 로
   개선되지만 거리는 그대로다. **둘 다 좋아지지는 않는다.**

### 8-5. 아직 확인 못 한 것

- 지방 10곳은 임의로 고른 좌표라 대표성이 제한적이다
- 점수 가중치(회전 ×3 · 상승 ×0.5 · 진입 100m당 1점 · 거리 1km당 10점)는 훑어봤으나
  결과가 거의 안 움직였다. 근거 있는 값이 아니라 감으로 잡은 값이다
- 신호등·횡단보도, 노면(`surface`), 경사 분포는 아직 안 쟀다. **길품질은 여전히 길 종류
  이름표만 보고 매긴 점수다** — 대로변 보도와 한강 산책로가 같은 `footway` 로 1.00 이다
