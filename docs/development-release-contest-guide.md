## 0. 문서 지위와 판단 순서

충돌하면 아래 순서로 판단한다.

1. **공모전 공식 공지·제출 화면·운영사무국 회신** — 제출 자격, 기한, 양식, 심사 규정
2. **제출 스토어의 최신 정책·콘솔 실제 안내** — 스토어 승인과 배포 정책.
   지금 경로는 **원스토어**다(#253) — 원스토어 개발자 문서·공지가 먼저이고,
   Google Play 문서는 `[Play 전환 시]` 참고다
3. **`SPEC.md`** — 런닝구 제품 범위와 정책의 SSOT
4. **API 명세·화면/API 매핑표·`AGENTS.md`** — 구현 계약과 작업 절차
5. **이 문서** — 일정, 체크리스트, 운영 절차

공식 공지와 저장소 계약이 충돌하면 임의로 해석하지 않는다. 공모전 관련 내용은 운영사무국 또는 OpenAPI 문의처에, 위치정보 관련 내용은 위치정보지원센터에 확인한 뒤 회신과 결정을 문서에 남긴다.

### 제출일을 날짜로 박지 않는 이유

**원스토어 심사는 영업일 최대 5일**이다 🔒확인 (2026-09-07 · [공식 검증 요청 안내](https://onestore-dev.gitbook.io/dev/docs/apps/request-for-review)). **예외 상황에서는 연장될 수 있고**, 미국 배포에 붙는 추가 기간과는 다른 이야기다.

```
공개 목표      09-11 (늦어도)
심사 소요일    영업일 최대 5일 (연장 가능)
제출일         역산하면 이미 지났다  →  준비되는 즉시 제출
```

**최대치를 그대로 빼면 제출일이 오늘 이전이다.** 그래서 날짜를 정해 기다리는 것이 아니라 **준비가 끝나는 즉시 제출한다.** 09-11 공개 목표는 유지하되 **승인을 보장하는 날로 적지 않는다** — 심사 기간은 상한이지 약속이 아니다.

- **심사 승인일을 확정 일정처럼 적지 않는다.** 우리가 정하는 날이 아니다
- 종전에 있던 `09-12 제출 · 09-17 공개` 는 **Play 기준으로 잡혔던 날짜**였고, 09-11 공개 목표와 맞지 않아 뺐다
- 09-11 을 넘기면 공모전 제출 자료의 "공개된 앱" 요건이 위태로워진다. 그 시점에 상태를 다시 판단한다

| 즉시 적용 | 승인이 끝나면 자동으로 배포 |
| 직접 적용 | 개발자가 직접 눌러야 배포 |
| 예약 적용 | 지정한 날짜에 자동 배포 |

**베타로 등록한 앱은 「직접 적용」만 쓸 수 있다.**

공모전 제출에는 **공개 링크가 필요**하다. 승인만 받고 배포를 안 눌러 두면 **링크가 생기지
않는다** — 승인 통보를 공개로 읽지 않는다.

### 아직 모르는 것 — 문의로 채운다

상한이 영업일 5일이라는 것만으로는 제출 시점을 계산할 수 없다. 다음이 있어야 한다.

- **접수일 산입 여부와 당일 접수 마감 시각**
- **반려 후 재검증의 소요일·산정 방식** — 처음부터 다시인가, 남은 일수만인가
- **승인 후 공개 옵션별 실제 공개 시점과 스토어 링크 반영 시점**

개발자센터 문의 또는 `devhelper@onestore.net` 으로 보낸다. **콘솔 소유자(이건모)가 보낸다.**
답이 오면 이 절을 고친다. **아직 보내지 않았다.**

### 4.2 브랜치와 PR

```text
develop → feature/*·fix/* → develop PR → 리뷰·CI → Squash merge
develop → main PR → 리뷰·릴리스 검증 → merge → vX.Y.Z tag
```

## 5. 한국관광공사 OpenAPI 운영 지침

### 5.1 심사 인정 조건

**[공식]** 한국관광공사 OpenAPI 사용은 선택이 아니라 필수다.

- 파일데이터만 쓰는 서비스는 인정되지 않는다.
- 제출한 인증키를 통해 개발 기간의 API별 호출 이력을 확인할 수 있다.
- 기능설명서에서 실제 서비스 화면과 활용 API를 확인한다.
- 개발 완료 서비스가 안정적으로 동작해야 한다.

따라서 릴리스 앱에서 `SAMPLE`·`SYNTH`만으로 심사 핵심 흐름을 구성하지 않는다. 폴백을 쓰더라도 실제 API 사용 화면, 원천 enum, 호출 시각과 캐시 시각, 출처를 추적할 수 있어야 한다.

### 5.2 실시간 호출·캐시·DB 저장 주의

공식 FAQ는 데이터 동기화 오류와 호출 이력 검증 때문에 **실시간 호출을 강하게 권고**하며, 부득이하게 로컬 DB 저장 방식을 쓰면 별도 신청서와 OpenAPI 문의가 필요하다고 안내한다.

현재 런닝구는 서버 Caffeine TTL 캐시와 두루누비 메타 동기화를 설계하고 있으므로 다음을 출시 게이트로 둔다.

- [ ] 사용자 기능에서 KTO OpenAPI를 실제 호출하고 개발·심사 기간 호출 이력을 유지
- [ ] 영속 저장 대상, TTL, 갱신 주기, 원본 삭제 의미를 목록화
- [ ] 단기 메모리 캐시와 영속 DB 저장을 구분해 기능설명서에 정확히 설명
- [ ] 두루누비 등 영속 동기화가 공식 FAQ의 별도 신청 대상인지 `tourapi@knto.or.kr`에 서면 확인
- [ ] 별도 신청이 필요하면 승인·회신을 제출 자료와 팀 보관소에 보관
- [ ] API 오류를 샘플 성공처럼 위장하지 않고 `LIVE/SAMPLE/SYNTH`를 UI까지 전달

### 5.3 키와 호출 증빙

- KTO 신청자별 **인코딩키·디코딩키 일체**는 공모전 제출 화면에만 입력한다.
- 운영계정 신청은 공식 안내상 선택이며, 활용 API 중 대표 1개를 신청할 수 있다.
- 인증키·호출 원문·개인 좌표를 Git, Markdown, 이슈, PR, 로그, 스크린샷에 남기지 않는다.
- 증빙에는 키 대신 신청자, API명, 호출 기간, 성공/오류 건수, 서비스 화면, 출처 문구를 남긴다.
- 서버 로그는 토큰·이메일·사용자 좌표를 마스킹하거나 기록하지 않고 `traceId`, 안정적 오류 `code`, API 작업명만 사용한다.

### 5.4 출처·저작권

- 허용 예: `출처: ⓒ한국관광공사`, `출처: ⓒ한국관광콘텐츠랩`
- 지양: `TourAPI`만 단독 표기
- 공사의 공식 CI/BI 로고 이미지는 무단 사용하지 않는다.
- KTO 이미지의 `cpyrhtDivCd`와 각 원천 라이선스를 준수한다.
- OSM 생성 경로는 `© OpenStreetMap contributors`를 표시한다.
- 서비스명·로고·스토어 설명이 한국관광공사가 직접 개발·운영하는 공식 앱처럼 보이지 않게 한다.

**그래도 스스로 비대상이라고 단정하지 않는다.** 법적 해석은 구조에 따라 달라지므로 아래를 지킨다.

- [ ] 갱신된 DFD 와 전송 필드·보관 기간·로그 정책 작성
- [ ] [위치정보지원센터](https://www.lbsc.kr/)에 공식 검토 요청 — 상담 02-588-0185 (이슈 #195)

### 6.2 개인정보처리방침 — 스토어 공통

**원스토어는 개인정보를 수집하는 앱에 개인정보 처리방침 URL 등록을 요구한다.** 공개된 URL 과 앱 내부 접근 경로가 필요하고, URL 은 활성 상태이며 공개 접근 가능해야 한다. PDF 가 아닌 비편집 웹 페이지여야 한다.

> 페이지 자체는 `web/privacy/index.html` 로 만들어 두었다(#303 으로 들어온다). 게시 조건과
> 남은 값은 `web/README.md` 에 있다. **게시일은 앱 공개 목표일과 다르다** — 웹 방침은
> **심사 제출 전**에 준비돼 있어야 한다.

개인정보처리방침에는 최소 다음을 포함한다.

- 앱명·개발자/운영 주체·개인정보 문의 수단
- 수집·접근하는 데이터: 이메일, 닉네임, 로그인 식별자, 위치, 저장 동선·코스 등 실제 출시본 기준
- 이용 목적, 제3자/SDK·외부 API 전송, 암호화와 접근 통제
- 보관 기간과 탈퇴·삭제 정책
- 위치정보의 단말 사용/서버 전송/저장 여부
- 마케팅 동의의 선택성과 철회 방법

스토어의 데이터 수집·공유 답변은 앱·서버·SDK 의 실제 동작, 그리고 개인정보처리방침과 **셋 다 일치**해야 한다. 항목 이름은 스토어마다 다르므로 콘솔의 실제 항목명으로 대조한다(9.5).

> **[Play 전환 시]** Play Console 의 **Data safety** 양식과 민감 권한 신고(포그라운드
> 서비스 등) 서술이 별도로 필요하다. 이번 원스토어 제출 범위가 아니다.

### 6.3 계정 삭제

앱에서 계정을 만들 수 있으므로 **앱 내부에 발견 가능한 계정 삭제 요청 경로**가 있어야 한다. 마이 > 설정 > 회원 탈퇴가 그것이고, 개인정보처리방침 8장에도 적혀 있다.

삭제는 단순 비활성화가 아니라 관련 사용자 데이터 삭제가 원칙이다. 법적·보안상 보존할 데이터가 있으면 대상과 기간을 개인정보처리방침에 명시한다.

> **[Play 전환 시]** Play 는 **앱 밖의 공개 웹 삭제 요청 URL** 을 추가로 요구하고 Play
> Console 에 제출하게 한다. **원스토어 등록 입력란에는 그 항목이 없다**(2026-09-06 개발자센터
> 문서 확인). 다만 *"입력란이 없다"* 와 *"삭제 요청 경로가 필요 없다"* 는 다른 말이고,
> 위의 앱 내부 경로는 지금도 제공한다. 실제 등록 폼 확인은 콘솔 소유자가 한다.

### 6.4 위치 — **권한을 선언하지 않는다** 🔒확정(SPEC 결정-56)

- Manifest 에 `ACCESS_FINE_LOCATION` · `ACCESS_COARSE_LOCATION` · `ACCESS_BACKGROUND_LOCATION` ·
  `FOREGROUND_SERVICE_LOCATION` 이 **하나도 없어야 한다.** merged debug/release Manifest 로 확인한다.
- `play-services-location` 의존성이 그래프에 없어야 한다.
- 코스 탐색 출발지는 검색·프리셋·S7 숙소뿐이다. 위치 권한이 없어도 **폴백이 아니라 정상 경로**다.
- 위치 포그라운드 서비스를 쓰지 않으므로 Play Console FGS 신고 대상이 아니다.
- Wi-Fi AP·기지국 Cell-ID·BLE·IP GeoIP 로 위치를 추정하지 않는다 — 스토어의 데이터 수집·공유 답변도 이 기준으로 적는다.

## 7. 백엔드·데이터베이스 배포 지침

### 7.1 배포 단위

| 단위 | 역할 | 현재 기준 |
|---|---|---|
| Spring Boot JAR | 인증·대회·동선·마이·외부 API 프록시 | Java 21, `bootJar` |

| GraphHopper 프로세스 | 적격 큐레이션 0건일 때 OSM 순환 경로 | EC2 server-only 별도 프로세스, 외부 builder가 만든 버전별 graph artifact |
| 데이터 Importer | canonical 대회 snapshot 적재 | 서버 시작 자동 실행 금지, 명시 실행 |
| Android 앱 | 사용자 클라이언트 | 운영 서버만 호출, KTO·카카오 REST 직호출 금지 |

### 7.2 환경 분리

최소 `local`, `staging`, `production`을 분리한다.

| 항목 | local | staging | production |
|---|---|---|---|
| DB | Docker PostgreSQL | 별도 DB | 별도 DB+백업 |
| 앱 API URL | `10.0.2.2`/개발 IP | 스테이징 HTTPS | 운영 HTTPS |
| 외부 API 키 | 개발 키 | 스테이징/개발 키 | 제출에 연결된 운영 키 |
| 사용자 데이터 | 가짜 데이터 | 심사용 가짜 계정 | 실제 사용자 데이터 |
| 로그 | 상세 가능, 시크릿 금지 | 제한 | 최소·구조화·보존기간 적용 |
| Swagger | 개발 편의 | 기본 비활성, 필요할 때만 접근 통제 후 활성 | 비활성 또는 접근 통제 |

스테이징과 운영의 DB·JWT·SMTP·외부 API 키를 공유하지 않는다.

### 7.3 운영 시크릿

서버 환경변수로만 주입한다.

- `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`
- KTO 인코딩/디코딩 서비스 키
- 카카오 REST 키
- SMTP 자격증명
- JWT 서명 키
- 필요 시 GraphHopper·스토리지 설정

키를 `.env`, 명령 출력, Docker 이미지, 앱, GitHub Actions 로그, 제출 PDF에 넣지 않는다. 운영 배포 계정에는 최소 권한을 적용하고 담당자 변경 시 회수한다.

### 7.5 배포·롤백 절차

머지 전 8GiB 검증에는 [GraphHopper artifact 계약 §11.1](deploy/graphhopper-artifact-contract.md#111-머지-전-staging-검증용-백엔드-묶음)의
PR head 전용 CI 묶음을 staging에서만 사용한다. 정식 릴리스·`main` 변경·자동 배포를 뜻하지 않는다.
머지 후에는 통합 commit의 CI 묶음을 다시 만들며 PR 검증용 묶음을 이름만 바꿔 승격하지 않는다.

2026-09-04 PR #255 머지 후 `develop` CI 묶음의 staging 전환·스모크는
[별도 배포 기록](deploy/evidence/staging-develop-1c3f2ef-20260904.md)에 남겼다.
같은 날 #263 머지 후 연령 검증이 포함된 `b9e632d`의 staging 재배포·입력 거부 시험은
[후속 배포 기록](deploy/evidence/staging-develop-b9e632d-20260904.md)에 남겼다.
그 다음 [앱 API 부하 시험 계획](deploy/api-load-test-plan.md)은 **기준 승인·실행 준비 중**이며,
기존 GraphHopper 직접 요청 검증이나 프로덕션 전체 체크리스트의 완료를 대신하지 않는다.
그 계획의 upstream guard는 staging 부하 시험용 쿼터 보호 장치이며 SPEC·HTTP API·캐시·재시도·
폴백 계약을 바꾸는 프로덕션 기능이 아니다.

1. 릴리스 후보 커밋에서 Android·백엔드 전체 테스트를 실행한다.
2. 백엔드 JAR·데이터 snapshot·GraphHopper graph artifact의 SHA-256, Git commit 또는 builder
   digest, 환경 이름을 릴리스 기록에 남긴다.
3. 스테이징에 동일 artifact를 배포하고 GraphHopper manifest 검증·활성화와 전체 스모크 테스트를
   실행한다.
4. 운영 DB를 백업하고 새 서버 버전을 배포한다.
5. Flyway 결과, 애플리케이션 기동, 외부 API, GraphHopper, SMTP를 확인한다.
6. Android 운영 빌드가 실제 운영 URL에 연결되는지 확인한다.
7. 치명 오류면 DB를 임의로 되돌리지 않고, 호환되는 직전 서버 artifact로 복귀한다. 마이그레이션 역호환이 없으면 정해진 복구 절차를 따른다.
8. hotfix는 `main`에서 `hotfix/*`를 만들고 `main`과 `develop` 양쪽에 반영한다.

GraphHopper graph 생산·manifest·활성화 계약은
[`deploy/graphhopper-artifact-contract.md`](deploy/graphhopper-artifact-contract.md), AWS EC2
스테이징의 전체 파일 배치·실행 명령·검증·롤백은
[`deploy/aws-ec2-staging-runbook.md`](deploy/aws-ec2-staging-runbook.md)를 따른다. 두 실행서는 이
절의 구현판이며 정책이나 절차가 충돌하면 §7이 우선한다.

## 9. Android·스토어 출시 지침

> **출시 경로는 원스토어다** 🔒확정(#253 · 2026-09-03). `APK + ONE store 앱 서명 **미사용**`.
> Play 경로는 신규 개인 계정 요건(12명 × 14일) 때문에 09-21 마감을 못 맞춰서 접었다.
> **AAB 전환은 공모전 이후 별도 결정**으로 남긴다. 아래 Play 관련 내용은 그때를 위한 참고다.

### 9.1 계정과 배포

- **원스토어 개발자 계정으로 APK를 등록한다.** 판매자 정보·IARC 설문은 콘솔 소유자가 입력한다.
- **심사는 영업일 최대 5일이다** 🔒확인 (2026-09-07 · [공식 검증 요청 안내](https://onestore-dev.gitbook.io/dev/docs/apps/request-for-review)).
  **예외 시 연장될 수 있고** 미국 배포에 붙는 추가 기간과는 구분된다. 상한이지 약속이 아니므로
  3장은 제출일을 날짜로 박지 않는다 — 준비되는 즉시 제출한다.
- 심사자와 공모전 제출팀이 설치할 버전은 **스토어에서 배포한 동일 `applicationId` 빌드**로 확인한다. 손으로 옮긴 로컬 APK 로 대신하지 않는다.

> **Play 전환 시** — 신규 개인 계정은 프로덕션 공개 전에 12명 이상이 14일 연속 참여한 비공개 테스트가 필요하고, 요건 충족 뒤 프로덕션 액세스를 신청하며 검토는 통상 7일 이내지만 더 길어질 수 있다.

### 9.2 빌드·서명·버전

- **산출물은 APK다** 🔒확정. `assembleRelease` 로 만든다.
- **원스토어가 재서명하지 않는다.** 우리 릴리스 키로 서명한 APK 가 그대로 사용자에게 간다 — 그래서 **사용자 기기에 깔리는 인증서 = 우리 릴리스 키**이고, 카카오 키 해시도 그 하나가 기준이다.
- ⚠️ **AAB 로 한 번 전환하면 APK 로 돌아올 수 없다.** 원스토어 공식 문서 기준이며, 전환 시에는 기존과 **동일한 앱 서명 키**를 등록해 쓴다.
- 릴리스 keystore·비밀번호는 저장소·메신저·문서에 넣지 않고 승인된 비밀 저장소에 보관한다. **원본·사본·오프라인 백업의 소재를 기록으로 남긴다** — 이 키를 잃으면 앱 업데이트가 영구히 불가능하다(재서명이 없으므로).
- `versionCode`는 업로드마다 증가시키고 `versionName`은 Git tag·제출 기록과 일치시킨다.
- **[Play]** 2026-08-31 부터 새 앱·업데이트는 Android 16, API 36 이상을 target 해야 한다
  ([타깃 API 수준 요건](https://support.google.com/googleplay/android-developer/answer/11926878)).
  **이것은 Google Play 정책이며 스토어 공통 의무가 아니다.**
- **[원스토어]** 2026-09-01 부터 **target API 최소 33** 이다 🔒확인 (2026-09-07 ·
  [원스토어 공지](https://dev.onestore.net/devpoc/support/news/noticeView.omp?noticeId=33671)).
  현재 `targetSdk=36` 이라 **충족한다.** Play 기준(API 36 이상)과 숫자가 다르므로 스토어별로
  따로 적는다 — 한쪽을 충족했다고 다른 쪽이 확인되는 것이 아니다.
- 릴리스 빌드에서 debug 로그, 샘플 메뉴, 개발 서버 URL, 테스트 키를 제거한다.
- R8을 활성화하고 Retrofit serialization, 카카오 SDK, Compose navigation, reflection 사용 지점의 release 회귀를 확인한다.

> **Play 전환 시** — AAB 로 제출하고 Play App Signing 을 쓰며, upload key 와 app signing key 의 역할이 갈린다. 그때는 카카오 키 해시가 **두 개**가 된다.

### 9.3 카카오 콘솔

- 패키지명: `com.runninggu.app`
- 디버그와 릴리스 키 해시를 각각 등록한다.
- **원스토어 앱 서명 미사용이므로 릴리스 키 해시는 하나다.** 우리가 서명한 APK 가 그대로 배포되기 때문이다.
- 개발자 PC 가 늘면 디버그 해시도 늘어난다. **콘솔에는 값만 나열되고 라벨을 달 수 없으므로**, 어느 해시가 무엇인지 이슈에 기록해 둔다(#108 · #296).
- 네이티브 앱 키만 Android `BuildConfig`에 주입한다.
- KTO·카카오 REST 키는 서버에만 둔다.
- 스토어 설치본에서 지도·로그인·공유를 검증한다.

> **Play 전환 시** — Play Console 의 **앱 서명 인증서** 기준 키 해시도 등록해야 한다. AAB 를 한 번 올려야 그 값이 콘솔에 나오므로 등록이 두 번에 나뉜다.

### 9.4 스토어 등록자료

**실제 값과 준비 상태는 [`docs/store/store-listing.md`](./store/store-listing.md) 가 원본이다.** 여기에는 규격만 적는다 — 두 곳에 값을 두면 갈라진다.

| 자료 | **원스토어** 기준 |
|---|---|
| 앱명 | `런닝구(區)` — `SPEC.md` 확정 표기 |
| 대표 아이콘 | **512×512** JPG·PNG |
| **그래픽 이미지** | **1024×578** JPG·PNG — 스토어 목록 상단 배너 |
| 스크린샷 | **2~8장 · 1,300×1,300 이하 · 장당 1MB 이내** · 세로 **720×1280 권장** |
| 한줄 설명 | 최대 100자. 과장·순위·가격·설치 유도 문구 금지 |
| 상세 설명 | 최대 1,300자. 실제 출시 기능, 데이터 출처, 지원 범위, 계정 사용 설명 |
| 판매자 정보 | 판매자명·공식 E-mail·전화번호·웹사이트 |
| 개인정보 처리방침 | 공개 웹 URL + 앱 내부 링크 |

> **[Play 전환 시]** 값이 다르다. **기능 그래픽은 1024×500** 이라 원스토어의 1024×578 과
> 크기가 달라 **다시 만들어야 한다.** 아이콘은 512×512 32-bit PNG·최대 1,024KB 이고,
> **계정 삭제 URL** 항목이 추가된다(6.3).

스토어 이미지에 한국관광공사 CI/BI 로고, 스토어 배지, 타사 상표를 무단 사용하지 않는다. 스크린샷은 목업이 아니라 해당 `versionCode`의 실제 앱 화면이어야 한다.

### 9.5 스토어 앱 콘텐츠 답변

> 항목 이름은 스토어마다 다르다. **원스토어 콘솔의 실제 항목명으로 대조**하고, 없는 항목은
> "해당 없음" 으로 남긴다 — 빈칸으로 두면 안 한 것과 구별되지 않는다.

- [ ] 개인정보처리방침
- [ ] 데이터 수집·공유 답변 (Play 의 Data safety 에 해당) — 앱·서버·카카오 SDK·지도 SDK·SMTP를 포함한 실제 데이터 흐름과 일치
- [ ] 광고 포함 여부
- [ ] 앱 액세스 — 심사 전용 계정과 제한 기능 진입 방법
- [ ] 대상 연령·타깃 사용자
- [ ] 콘텐츠 등급 설문
- [ ] 민감 권한 신고 — 위치 권한·포그라운드 서비스는 **선언하지 않으므로 해당 없음**(결정-56)
- [ ] 국가/지역 배포 범위·가격(무료 여부)

> **[Play 전환 시]** **계정 삭제 URL** 과 **Data safety** 양식이 추가된다(6.2 · 6.3).

### 9.6 출시 Go/No-Go

아래가 하나라도 실패하면 공모전 제출용 프로덕션 공개를 진행하지 않는다.

- [ ] **스토어에서 설치한** release 앱이 운영 서버에만 연결
- [ ] 앱 시작·게스트·로그인·카카오 로그인·회원가입·재설정 성공
- [ ] 동선 생성·코스·찜·마이 저장과 재로그인 복원 성공
- [ ] 심사 전용 계정으로 개인 정보 없이 전 기능 재현
- [ ] KTO 실호출과 올바른 출처 문구 확인
- [ ] 릴리스 키·REST 키·DB·JWT·SMTP 시크릿 노출 없음
- [ ] 개인정보처리방침·스토어 데이터 수집·공유 답변·실제 동작 일치

- [ ] 스토어 링크를 로그아웃 브라우저와 새 Android 기기에서 열어 설치 가능

6. 제출 뒤 다른 팀원이 모든 입력값·첨부·링크를 교차 검수한다.
7. 9월 21일 16시 전에는 수정할 수 있으나 팀 내부 마감 이후에는 치명 오류만 대표 승인으로 수정한다.
8. 최종 제출 시각, 접수 화면, 파일명·SHA-256을 보관한다. 화면에 인증키·비밀번호가 보이면 캡처하지 않는다.

- 개인 계정 제출 금지

- 이메일 인증, 첫 로그인 동의, 비밀번호 만료, 잠금, 카카오 추가 인증 없이 즉시 로그인되게 준비
- 심사 기간 계정을 삭제·초기화하지 않고 서버가 상시 동작하게 유지

#### 한국관광공사 OpenAPI 활용 정보

- 개발에 활용한 API 신청자별 인코딩키·디코딩키 일체

## 11. 제출 후 운영과 최종 발표 준비

### 11.1 1차 심사 기간 운영

- 공모전 제출 시점의 앱 버전과 서버 API 호환성을 유지한다.
- 치명 장애 외 기능 변경을 동결하고, hotfix는 재현·리뷰·회귀 테스트 후 배포한다.
- 심사 계정 로그인 성공 여부를 정기 확인하되 심사자 활동을 추적하거나 개인화하지 않는다.
- 운영 서버·DB·GraphHopper·SMTP·KTO 쿼터를 모니터링한다.
- 공모전 제출 링크와 **개인정보처리방침 URL** 을 유지한다. **앱 밖 계정 삭제 URL 은 원스토어
  경로에서 요구 항목이 아니다** — 삭제는 앱 안의 회원 탈퇴로 제공하며, 그 경로가 계속 동작하는지
  확인한다. `[Play 전환 시]` 외부 삭제 URL 도 상시 유지 대상이 된다.
- 장애가 심사 재현에 영향을 주면 원인·기간·복구 버전을 기록하고 운영사무국 문의 필요 여부를 대표가 판단한다.

### 11.2 최종 발표 패키지

- 문제→사용자→핵심 흐름→KTO 데이터 가치→차별성→운영·발전 순서의 발표자료
- 실제 스토어 설치본 라이브 데모
- 네트워크 실패에 대비한 동일 버전의 2~3분 화면 녹화
- 데모용 전용 계정과 초기화된 시나리오 데이터
- API·DFD·개인정보·위치정보·운영 구조 질문 답변
- 평가 항목별 한 문장 근거와 실제 화면
- 발표 기기, 보조 기기, 충전, 네트워크, 화면 비율, 알림 차단 점검

## 12. 역할과 승인

운영 주체는 **루트메이트**다. 루트메이트는 런닝구(區)를 개발·운영하는 팀이다. 팀 대표이자
AWS·도메인·Google Play 계정 및 인프라 운영책임자는 **유선경**이다. 개인정보 문서에는 실명
대신 담당 부서 `루트메이트 개인정보보호 담당`과 `runninggu.play@gmail.com`을 공개하고,
실명은 필요한 계약·계정 문서에서 사용한다(#230). 기존 담당 영역은 `AGENTS.md`를 따른다.
`privacy@runninggu.store` 수신 주소와 MX는 구성하지 않고 위 Gmail 주소를 공개 문의처로 쓴다.

한 사람이 여러 출시 역할을 맡을 수 있지만 대리인은 실제 배포 전에 반드시 적는다.

| 역할 | 기본 담당 영역 | 확정할 것 |
|---|---|---|
| 앱 릴리스 | 앱 UI·앱 코어 공동 | **원스토어 콘솔 업로드**(`[Play 전환 시]` Play Console), 서명키 접근자, 스토어 자료 최종 검수자 |
| 백엔드 운영 | 유선경 | 호스팅·DB·GraphHopper 배포, 백업·장애 대응 대리인 |
| API·데이터 증빙 | 백엔드+앱 코어 | KTO 신청자 키 제출 책임자, 호출 증빙 검수자 |
| 개인정보·위치정보 | 루트메이트 개인정보보호 담당 | 정책 문서 책임자, 위치정보지원센터 문의·신고 책임자 |
| 공모전 제출 | 팀 대표 | 콘텐츠랩 입력자, 교차 검수자, 마감 대응 대리인 |
| 최종 발표 | 발표자+데모 담당 | 발표자, 라이브 데모 담당, 장애 시 녹화 전환 기준 |

외부 계정은 개인 소유로 방치하지 않는다. 계정 소유자, 복구 이메일, 2단계 인증, 대리 접근, 프로젝트 종료 후 인수인계 방법을 팀 비밀 저장소에 기록한다.
