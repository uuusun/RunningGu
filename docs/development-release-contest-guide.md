## 0. 문서 지위와 판단 순서

충돌하면 아래 순서로 판단한다.

1. **공모전 공식 공지·제출 화면·운영사무국 회신** — 제출 자격, 기한, 양식, 심사 규정
2. **Google Play 최신 정책·Play Console 실제 안내** — 스토어 승인과 배포 정책
3. **`SPEC.md`** — 런닝구 제품 범위와 정책의 SSOT
4. **API 명세·화면/API 매핑표·`AGENTS.md`** — 구현 계약과 작업 절차
5. **이 문서** — 일정, 체크리스트, 운영 절차

공식 공지와 저장소 계약이 충돌하면 임의로 해석하지 않는다. 공모전 관련 내용은 운영사무국 또는 OpenAPI 문의처에, 위치정보 관련 내용은 위치정보지원센터에 확인한 뒤 회신과 결정을 문서에 남긴다.

## 4. 개발 지침

### 4.1 범위와 완료 기준

1. 제출 버전은 `SPEC.md` §11의 **P0 전체**를 기준으로 한다.
2. 카카오 공유·이동시간 등 P1 항목은 실제 릴리스에 포함되고 검증된 경우에만 기능설명서에 쓴다. GPS 러닝 기록은 제품에 없다(결정-56).
3. 범위 제외인 커뮤니티·인기 대회·동선 산책 블록은 되살리지 않는다.
4. API·DTO·enum·DB·외부 API 계약이 없으면 구현을 멈추고 계약을 먼저 확정한다.
5. `docs/screen-api-matrix.md` §11의 springdoc 상세화 항목은 해당 API 출시 전에 모두 닫는다.
6. 모든 비동기 화면은 Loading/Content/Empty/Error를 구분하고 부분 실패 정책을 지킨다.
7. 기능 하나의 완료는 코드, 테스트, 명세, 운영 설정, 심사 재현 절차까지 포함한다.

### 4.2 브랜치와 PR

```text
develop → feature/*·fix/* → develop PR → 리뷰·CI → Squash merge
develop → main PR → 리뷰·릴리스 검증 → merge → vX.Y.Z tag
```

- 기준 브랜치는 `develop`, `main`은 배포된 릴리스만 유지한다.
- `main`·`develop` 직접 push 금지, 최소 1명 승인.
- 계약 변경과 관련 문서는 같은 PR에 넣는다.
- 릴리스 PR에는 변경 요약, DB 마이그레이션, 설정 변경, 롤백 방법, 검증 결과, 알려진 제약을 적는다.
- 공모전 제출본 태그 예: `v1.0.0`. 실제 버전과 태그는 Android `versionName`과 맞춘다.

### 4.3 최소 검증 명령

```powershell
# Android 단위 테스트·디버그 빌드
cd android
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug --console=plain

# 릴리스 산출물 (서명키·배포 주소는 local.properties 에서 읽는다 — README 「릴리스 빌드」)
# 둘 다 없어도 빌드는 되고 경고만 뜬다. 그 산출물은 스토어에 올릴 수 없다.
.\gradlew.bat :app:assembleRelease :app:bundleRelease --console=plain

# Backend 단위·PostgreSQL 통합 테스트·실행 JAR
cd ..\backend
.\gradlew.bat clean test bootJar --console=plain
```

추가 필수 검증:

- Android UI 변경: 실제 기기/에뮬레이터 스크린샷
- Android 릴리스: **Play 내부/비공개 테스트에서 설치한 앱**으로 실기기 E2E
- 백엔드: 스테이징 PostgreSQL과 동일 Flyway 경로, 배포 JAR 기동, OpenAPI 계약 확인
- 스크립트: 같은 입력으로 2회 실행해 바이트 단위 결정성 확인
- 외부 API: KTO·카카오·GraphHopper 정상/timeout/429/부분 장애 시나리오

## 5. 한국관광공사 OpenAPI 운영 지침

### 5.1 심사 인정 조건

**[공식]** 한국관광공사 OpenAPI 사용은 선택이 아니라 필수다.

- 파일데이터만 쓰는 서비스는 인정되지 않는다.
- 제출한 인증키를 통해 개발 기간의 API별 호출 이력을 확인할 수 있다.
- 기능설명서에서 실제 서비스 화면과 활용 API를 확인한다.
- 개발 완료 서비스가 안정적으로 동작해야 한다.

따라서 릴리스 앱에서 `SAMPLE`·`SYNTH`만으로 심사 핵심 흐름을 구성하지 않는다. 폴백을 쓰더라도 실제 API 사용 화면, 원천 enum, 호출 시각과 캐시 시각, 출처를 추적할 수 있어야 한다.

### 5.2 실시간 호출·캐시·DB 저장 주의

공식 FAQ는 데이터 동기화 오류와 호출 이력 검증 때문에 **실시간 호출을 강하게 권고**하며, 부득이하게 로컬 DB 저장 방식을 쓰면 별도 신청서와 OpenAPI 문의가 필요하다고 안내한다.

현재 런닝구는 서버 Caffeine TTL 캐시와 두루누비 메타 동기화를 설계하고 있으므로 다음을 출시 게이트로 둔다.

- [ ] 사용자 기능에서 KTO OpenAPI를 실제 호출하고 개발·심사 기간 호출 이력을 유지
- [ ] 영속 저장 대상, TTL, 갱신 주기, 원본 삭제 의미를 목록화
- [ ] 단기 메모리 캐시와 영속 DB 저장을 구분해 기능설명서에 정확히 설명
- [ ] 두루누비 등 영속 동기화가 공식 FAQ의 별도 신청 대상인지 `tourapi@knto.or.kr`에 서면 확인
- [ ] 별도 신청이 필요하면 승인·회신을 제출 자료와 팀 보관소에 보관
- [ ] API 오류를 샘플 성공처럼 위장하지 않고 `LIVE/SAMPLE/SYNTH`를 UI까지 전달

### 5.3 키와 호출 증빙

- KTO 신청자별 **인코딩키·디코딩키 일체**는 공모전 제출 화면에만 입력한다.
- 운영계정 신청은 공식 안내상 선택이며, 활용 API 중 대표 1개를 신청할 수 있다.
- 인증키·호출 원문·개인 좌표를 Git, Markdown, 이슈, PR, 로그, 스크린샷에 남기지 않는다.
- 증빙에는 키 대신 신청자, API명, 호출 기간, 성공/오류 건수, 서비스 화면, 출처 문구를 남긴다.
- 서버 로그는 토큰·이메일·사용자 좌표를 마스킹하거나 기록하지 않고 `traceId`, 안정적 오류 `code`, API 작업명만 사용한다.

### 5.4 출처·저작권

- 허용 예: `출처: ⓒ한국관광공사`, `출처: ⓒ한국관광콘텐츠랩`
- 지양: `TourAPI`만 단독 표기
- 공사의 공식 CI/BI 로고 이미지는 무단 사용하지 않는다.
- KTO 이미지의 `cpyrhtDivCd`와 각 원천 라이선스를 준수한다.
- OSM 생성 경로는 `© OpenStreetMap contributors`를 표시한다.
- 서비스명·로고·스토어 설명이 한국관광공사가 직접 개발·운영하는 공식 앱처럼 보이지 않게 한다.

## 6. 위치정보·개인정보·법적 출시 게이트

### 6.1 위치기반서비스 검토

공식 공모전 FAQ의 기준:

- 위치정보를 단말 내부에서만 쓰고 서버에 전송하지 않으면 비신고 대상이 될 수 있다.
- 서비스 제공을 위해 개인위치정보를 사업자 서버로 전송하면 DB 저장 여부와 무관하게 신고 대상 기준에 해당한다.

**런닝구는 기기에서 사용자 위치를 얻지 않는다**(SPEC 결정-56 · 이슈 #215). 위치 권한도
`FusedLocationProvider` 도 없고, Wi-Fi AP·기지국 Cell-ID·BLE·IP GeoIP 로 위치를 추정하지도
않는다. `/courses/near`·POI·지오코딩에 나가는 좌표는 사용자가 **검색·프리셋·S7 숙소로 직접
고른 장소**의 좌표다.

**그래도 스스로 비대상이라고 단정하지 않는다.** 법적 해석은 구조에 따라 달라지므로 아래를 지킨다.

- [ ] 갱신된 DFD 와 전송 필드·보관 기간·로그 정책 작성
- [ ] [위치정보지원센터](https://www.lbsc.kr/)에 공식 검토 요청 — 상담 02-588-0185 (이슈 #195)
- [ ] **실제 APK·네트워크 흐름**을 근거로 제시한다 — 문서만으로 판단받지 않는다
- [ ] 대상으로 판정되면 신고와 이용약관·개인정보처리방침 반영을 그때 연다
- [ ] 구조를 되돌리는 변경(기기 위치 재도입)은 이 검토를 먼저 다시 받는다

확인 없이 "위치를 안 쓰니 괜찮다" 고 판단하지 않는다.

### 6.2 Google Play 개인정보 요건

**[Play]** 모든 앱은 공개된 개인정보처리방침 URL과 앱 내부 접근 경로가 필요하다. URL은 활성 상태이고 공개 접근 가능해야 하며 PDF가 아닌 비편집 웹 페이지여야 한다.

개인정보처리방침에는 최소 다음을 포함한다.

- 앱명·개발자/운영 주체·개인정보 문의 수단
- 수집·접근하는 데이터: 이메일, 닉네임, 로그인 식별자, 위치, 저장 동선·코스 등 실제 출시본 기준
- 이용 목적, 제3자/SDK·외부 API 전송, 암호화와 접근 통제
- 보관 기간과 탈퇴·삭제 정책
- 위치정보의 단말 사용/서버 전송/저장 여부
- 마케팅 동의의 선택성과 철회 방법

Play Console의 Data safety 답변은 앱, 서버, SDK의 실제 동작과 개인정보처리방침이 일치해야 한다.

### 6.3 계정 삭제

앱에서 계정을 만들 수 있으므로 다음 두 경로가 모두 필요하다.

1. 앱 내부의 발견 가능한 계정 삭제 요청 경로
2. 앱 외부의 공개 웹 삭제 요청 URL — Play Console에 제출

삭제는 단순 비활성화가 아니라 관련 사용자 데이터 삭제가 원칙이다. 법적·보안상 보존할 데이터가 있으면 대상과 기간을 개인정보처리방침에 명시한다.

### 6.4 위치 — **권한을 선언하지 않는다** 🔒확정(SPEC 결정-56)

- Manifest 에 `ACCESS_FINE_LOCATION` · `ACCESS_COARSE_LOCATION` · `ACCESS_BACKGROUND_LOCATION` ·
  `FOREGROUND_SERVICE_LOCATION` 이 **하나도 없어야 한다.** merged debug/release Manifest 로 확인한다.
- `play-services-location` 의존성이 그래프에 없어야 한다.
- 코스 탐색 출발지는 검색·프리셋·S7 숙소뿐이다. 위치 권한이 없어도 **폴백이 아니라 정상 경로**다.
- 위치 포그라운드 서비스를 쓰지 않으므로 Play Console FGS 신고 대상이 아니다.
- Wi-Fi AP·기지국 Cell-ID·BLE·IP GeoIP 로 위치를 추정하지 않는다 — Data safety 답변도 이 기준으로 적는다.

## 7. 백엔드·데이터베이스 배포 지침

### 7.1 배포 단위

| 단위 | 역할 | 현재 기준 |
|---|---|---|
| Spring Boot JAR | 인증·대회·동선·마이·외부 API 프록시 | Java 21, `bootJar` |
| PostgreSQL 17 | 온라인 SSOT | Flyway, UTC timestamp |
| GraphHopper 프로세스 | 적격 큐레이션 0건일 때 OSM 순환 경로 | 서버 내부 별도 프로세스, 영속 그래프 캐시 |
| 데이터 Importer | canonical 대회 snapshot 적재 | 서버 시작 자동 실행 금지, 명시 실행 |
| Android 앱 | 사용자 클라이언트 | 운영 서버만 호출, KTO·카카오 REST 직호출 금지 |

### 7.2 환경 분리

최소 `local`, `staging`, `production`을 분리한다.

| 항목 | local | staging | production |
|---|---|---|---|
| DB | Docker PostgreSQL | 별도 DB | 별도 DB+백업 |
| 앱 API URL | `10.0.2.2`/개발 IP | 스테이징 HTTPS | 운영 HTTPS |
| 외부 API 키 | 개발 키 | 스테이징/개발 키 | 제출에 연결된 운영 키 |
| 사용자 데이터 | 가짜 데이터 | 심사용 가짜 계정 | 실제 사용자 데이터 |
| 로그 | 상세 가능, 시크릿 금지 | 제한 | 최소·구조화·보존기간 적용 |
| Swagger | 개발 편의 | 제한 접근 | 비활성 또는 접근 통제 |

스테이징과 운영의 DB·JWT·SMTP·외부 API 키를 공유하지 않는다.

### 7.3 운영 시크릿

서버 환경변수로만 주입한다.

- `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`
- KTO 인코딩/디코딩 서비스 키
- 카카오 REST 키
- SMTP 자격증명
- JWT 서명 키
- 필요 시 GraphHopper·스토리지 설정

키를 `.env`, 명령 출력, Docker 이미지, 앱, GitHub Actions 로그, 제출 PDF에 넣지 않는다. 운영 배포 계정에는 최소 권한을 적용하고 담당자 변경 시 회수한다.

### 7.4 프로덕션 배포 전 체크

- [ ] 호스팅 사업자·리전·도메인·예산·결제 책임자 확정 **[결정 필요]**
- [ ] 운영 계정 소유자와 2단계 인증·복구 수단 확정 **[결정 필요]**
- [ ] HTTPS 인증서와 자동 갱신, 앱 `BASE_URL` 확정
- [ ] PostgreSQL 백업 주기·보존 기간·복구 절차와 실제 복구 리허설
- [ ] Flyway 마이그레이션 순서, 롤백이 아니라 전진 수정하는 기준 합의
- [ ] 다중 인스턴스라면 Flyway·Importer의 단일 실행 주체 확정
- [ ] `contestImport`를 명시 실행하고 동일 입력 no-op·오류 전체 롤백 확인
- [ ] GraphHopper PBF/SRTM 버전·그래프 캐시 영속성·메모리·기동 시간 확인
- [ ] KTO·카카오 timeout·캐시·레이트리밋·429 정책 확인
- [ ] SMTP 발신 도메인·스팸함·인증 코드·재설정 링크의 운영 도메인 확인
- [ ] 로그에 토큰·비밀번호·이메일·좌표가 없는지 샘플 검사
- [ ] 장애 감지·담당자 알림·운영사무국 심사 기간 대응 체계 확정
- [ ] 배포 직전 DB 백업과 직전 앱/서버 artifact 보관

### 7.5 배포·롤백 절차

1. 릴리스 후보 커밋에서 Android·백엔드 전체 테스트를 실행한다.
2. 백엔드 JAR과 데이터 snapshot의 SHA-256, Git commit, 환경 이름을 릴리스 기록에 남긴다.
3. 스테이징에 동일 artifact를 배포하고 전체 스모크 테스트를 실행한다.
4. 운영 DB를 백업하고 새 서버 버전을 배포한다.
5. Flyway 결과, 애플리케이션 기동, 외부 API, GraphHopper, SMTP를 확인한다.
6. Android 운영 빌드가 실제 운영 URL에 연결되는지 확인한다.
7. 치명 오류면 DB를 임의로 되돌리지 않고, 호환되는 직전 서버 artifact로 복귀한다. 마이그레이션 역호환이 없으면 정해진 복구 절차를 따른다.
8. hotfix는 `main`에서 `hotfix/*`를 만들고 `main`과 `develop` 양쪽에 반영한다.

| **BLOCKER** | 개인정보 공개 문서 없음 | 공개 URL·앱 내부 링크·외부 탈퇴 URL 없음 | 개인정보처리방침·Data safety·계정 삭제 양 경로 |
| **BLOCKER** | 공모전 심사 계정 없음 | 제출 전용 계정 절차 없음 | 공식 형식 전용 계정, 모든 제한 기능 접근, 새 기기 검증 |
| **REQUIRED** | 릴리스 버전 정책 | `versionCode=1`, `versionName=1.0` 초기값 | 태그·스토어 버전·변경기록 일치, 업데이트마다 code 증가 |
| **REQUIRED** | 릴리스 CI 없음 | CI가 debug test/build만 수행 | 서명 없는 release compile 검증 또는 승인된 안전한 서명 배포 절차 |
| **REQUIRED** | 스토어 등록자료 없음 | 아이콘·기능 그래픽·설명·정책 응답 미정 | Play Console 필수 항목과 실제 화면 이미지 완료 |
| **REQUIRED** | 운영 프로필 보강 | springdoc 운영 제한·운영 관측 설정 미정 | 프로덕션 설정과 접근 통제 검증 |

새 라이브러리, 공개 API, DB 스키마, 배포 사업자 선택은 담당자 합의 없이 이 표를 구현으로 먼저 확정하지 않는다.

## 9. Android·Google Play 출시 지침

### 9.1 계정과 테스트 트랙

- Play 개발자 계정이 **2023-11-13 이후 만든 신규 개인 계정**이면 프로덕션 공개 전에 12명 이상이 14일 연속 참여한 비공개 테스트가 필요하다.
- 요건 충족 뒤 프로덕션 액세스를 신청하며, 검토는 통상 7일 이내지만 더 길어질 수 있다.
- 내부 테스트 → 비공개 테스트 → 프로덕션 순으로 진행한다.
- 심사자와 공모전 제출팀이 설치할 버전은 로컬 APK가 아니라 Play에서 배포한 동일 applicationId의 빌드로 확인한다.

### 9.2 빌드·서명·버전

- 새 Google Play 앱은 Android App Bundle(AAB)로 제출한다.
- Play App Signing을 사용하고 upload key와 app signing key의 역할을 구분한다.
- upload keystore·비밀번호는 저장소·메신저·문서에 넣지 않고 승인된 비밀 저장소에 보관한다.
- `versionCode`는 업로드마다 증가시키고 `versionName`은 Git tag·제출 기록과 일치시킨다.
- 2026-08-31부터 새 앱·업데이트는 Android 16, API 36 이상을 target해야 한다. 현재 프로젝트의 `targetSdk=36`은 이 기준에 맞지만 실제 업로드 시 Play Console 정책을 다시 확인한다.
- 릴리스 빌드에서 debug 로그, 샘플 메뉴, 개발 서버 URL, 테스트 키를 제거한다.
- R8을 활성화하고 Retrofit serialization, 카카오 SDK, Compose navigation, reflection 사용 지점의 release 회귀를 확인한다.

### 9.3 카카오 콘솔

- 패키지명: `com.runninggu.app`
- 디버그와 릴리스 키 해시를 각각 등록한다.
- Play App Signing을 쓰면 Play Console의 **앱 서명 인증서** 기준 키 해시도 등록한다.
- 네이티브 앱 키만 Android `BuildConfig`에 주입한다.
- KTO·카카오 REST 키는 서버에만 둔다.
- 내부 테스트 설치본과 프로덕션 설치본에서 지도·로그인·공유(출시 시)를 각각 검증한다.

## 11. 제출 후 운영과 최종 발표 준비

### 11.1 1차 심사 기간 운영

- 공모전 제출 시점의 앱 버전과 서버 API 호환성을 유지한다.
- 치명 장애 외 기능 변경을 동결하고, hotfix는 재현·리뷰·회귀 테스트 후 배포한다.
- 심사 계정 로그인 성공 여부를 정기 확인하되 심사자 활동을 추적하거나 개인화하지 않는다.
- 운영 서버·DB·GraphHopper·SMTP·KTO 쿼터를 모니터링한다.
- 공모전 제출 링크와 개인정보처리방침·계정 삭제 URL을 유지한다.
- 장애가 심사 재현에 영향을 주면 원인·기간·복구 버전을 기록하고 운영사무국 문의 필요 여부를 대표가 판단한다.

### 11.2 최종 발표 패키지

- 문제→사용자→핵심 흐름→KTO 데이터 가치→차별성→운영·발전 순서의 발표자료
- 실제 스토어 설치본 라이브 데모
- 네트워크 실패에 대비한 동일 버전의 2~3분 화면 녹화
- 데모용 전용 계정과 초기화된 시나리오 데이터
- API·DFD·개인정보·위치정보·운영 구조 질문 답변

## 12. 역할과 승인

기존 담당 영역은 `AGENTS.md`를 따른다. 아래 출시 역할은 **[결정 필요]**이며 한 사람이 여러 역할을 맡을 수 있지만 이름과 대리인을 반드시 적는다.

| 역할 | 기본 담당 영역 | 확정할 것 |
|---|---|---|
| 앱 릴리스 | 앱 UI·앱 코어 공동 | Play Console 업로드, 서명키 접근자, 스토어 자료 최종 검수자 |
| 백엔드 운영 | 유선경 | 호스팅·DB·GraphHopper 배포, 백업·장애 대응 대리인 |
| API·데이터 증빙 | 백엔드+앱 코어 | KTO 신청자 키 제출 책임자, 호출 증빙 검수자 |
| 개인정보·위치정보 | 팀 대표+구조 담당 | 정책 문서 책임자, 위치정보지원센터 문의·신고 책임자 |
| 공모전 제출 | 팀 대표 | 콘텐츠랩 입력자, 교차 검수자, 마감 대응 대리인 |
| 최종 발표 | 발표자+데모 담당 | 발표자, 라이브 데모 담당, 장애 시 녹화 전환 기준 |

외부 계정은 개인 소유로 방치하지 않는다. 계정 소유자, 복구 이메일, 2단계 인증, 대리 접근, 프로젝트 종료 후 인수인계 방법을 팀 비밀 저장소에 기록한다.
