> [메모리 계약 §8.1](graphhopper-artifact-contract.md#81-적용-순서)을 현재 배포 기준으로 사용한다.
> 두 부하는 별도 시각에 실행했으며 2,100건 혼합 부하 합격으로 합산하지 않는다.

> 원래 2,100건 전체 용량 합격은 아니다. [상세 결과와 한계](evidence/api-load-ec2-4g-20260907-no-kto.md).

>

>

> TIMEOUT(2,707ms)·가드 TRIP으로 시작 전 중단했다. 예정 2,100건 모두 미실행이며
> 용량 판정은 보류다. 가드 OFF·readiness·HTTPS 복귀와 입력 폐기는 완료했다.
> [별도 실행 증거](evidence/api-load-ec2-4g-20260906-v3.md)를 따른다.

> 작성: 2026-09-06. 상태: **기본 운영 점검 완료(06:17:55Z)**.

> 기존 4GiB staging을 유지하면서 주요 기능·서비스 지속 실행·백업이 실제로 작동하는지 확인한다.

> **“4GiB 기본 운영 점검 완료”**이며 2,100건 부하 완주나 프로덕션 전체 출시 승인을 뜻하지 않는다.

## 1. 고정 범위

- 기존 `ap-northeast-2b`, `i-07aa483968f4daddc`, `c7i-flex.large` 4GiB를 유지한다.
- backend `673a2f796052f4553113d5cd25608fb3821222ac`, graph artifact
  `gh11-korea-20260901-2ff6731b181a-2b8515dd29fc`, GraphHopper heap 2GiB·backend heap 512MiB와
  각 프로세스 상한을 먼저 대조한다. 실제 문제의 근거 없이 설정을 먼저 바꾸지 않는다.
- 새 AWS 리소스를 만들지 않는다. 옛 2a 인스턴스는 정지 상태로 둔다.
- 정상 재부팅·Importer·장애 격리의 기존 증거는 관련 이미지·artifact·설정이 같은 경우 재사용한다.
- 35분 앱 부하·전체 시나리오 3회 연속·새로운 24시간 관찰은 추가 검증으로 보류한다.
  이미 지나간 시간은 남아 있는 로그로 확인한다. 계측하지 않은 과거 구간을 관찰 완료로 간주하지 않는다.
- 하루 방문 20회는 사용자의 초기 예상이다. 이를 API 요청 수나 보장 가능한 동시 사용자 수로 환산하지 않는다.

## 2. 실행 순서

### 1단계 — 도구 준비와 접속 복구

- 기존 승인 fixture·응답 검사·계정 분리 검사를 재사용하는 소량 점검 전용 실행 경로를 준비한다.
  `scripts/api/run_api_smoke.py`를 추가했다. 2,100건 스케줄을 호출하지 않고 요청별 결과를 즉시 저장한다.
- 예외·사용자 중단에도 부분 결과를 보존하고 세션·시험 쓰기를 정리한다. 비밀값·원문 응답·좌표는 저장하지 않는다.
- 전체 부하 미실행과 정상·오류·중단·정리를 검증한다. scripts 변경은 저장소 규칙대로 오프라인 검사와
  mock 실행을 2회 수행하며 실제 공급자를 결정성 검사 용도로 반복 호출하지 않는다.
- AWS 로그인 복구 후 실제 사양, backend/graph 버전, boot ID, 메모리 상한, 서비스,
  가드 비활성, 백업·WAL·인증서 갱신 timer를 읽기 전용으로 확인한다.

### 2단계 — 지난 실행 기록 확인

- **2026-09-05 13:00Z의 정상 복귀부터 조회 시각까지** kernel·systemd·Docker 기록을 확인한다.
- OOM·메모리 할당 실패·의도하지 않은 종료와 재시작을 서비스별 시각·원인·복구 상태로 정리한다.
- 계획된 재기동은 InvocationID·boot ID와 작업 기록으로 분리한다. GC 시작·완료 줄을 중복 집계하지 않는다.
- GC 횟수·정지 시간·GC 후 heap 사용량을 기록한다. GC·swap·순간 MemAvailable만으로 중단하지 않는다.
- 로그의 실제 보존 구간을 명시한다. 과거 응답시간·host 메모리 시계열이 없으면 그 항목은 미확인이다.

### 3단계 — 주요 앱 API 소량 점검 1회

1. 가드 비활성 상태의 공개 HTTPS 기본 7항목을 확인한다.
2. 새 run ID로 staging 가드를 켠다. KTO operation별 100, 카카오 전체 5,000·endpoint별 2,000을
   유지하고 실제 송신 계측·preflight를 확인한다. 이 전제가 확인되지 않으면 외부 연동 점검을 시작하지 않는다.
3. 기존 테스트 계정 A·B의 비밀값을 숨김 입력으로 받아 메모리에만 보관한다.
4. 승인 fixture의 **14종을 각 1회, 순차 실행**한다. 대회·코스 조회, curated/OSM 주변 코스,
   축제·POI·지오코딩·동선 생성·내 정보·즐겨찾기 목록을 포함한다.
5. 기존 계정 분리 검사로 전용 즐겨찾기의 추가·읽기·삭제와 A/B 분리를 한 번 확인한다.
   테스트 전용 계정·대상인지 확인하며 기존 사용자 데이터를 정리 대상으로 삼지 않는다.
6. 로그인·소유권 검사·정리·로그아웃은 14종과 구분해 집계한다. 요청별 기대/실제 status,
   내용 검사·시간·오류 분류를 남기며 실패 후 입력을 바꾸어 성공으로 덮지 않는다.
7. 문제 있는 읽기 요청은 같은 입력으로 최대 1회 추가 확인한다. 쓰기는 상태를 먼저 확인하고
   기존 멱등성·정리 계약을 따른다. 공급자 오류로 가드가 trip하면 추가 송신을 멈추고 정리한다.
   같은 run ID의 counter를 초기화해 재개하지 않는다.

자원은 점검 시작부터 **15분간 5초 간격**으로 기록해 요청 전후와 유휴 복귀를 본다.
15분은 관측 범위이며 그동안 추가 부하를 채워 넣지 않는다. 누락 표본은 구간과 근거 부족 여부를
기록한다. 소량 표본으로 p95 합격·최대 처리량을 주장하지 않고 캐시를 강제로 비우지 않는다.

### 4단계 — 자동 백업·WAL 확인

- 매일 03:20 KST 백업의 예약 실행 여부, 실제 마지막 full backup 완료 시각·label·결과를 확인한다.
  timer가 active인 것만으로 성공으로 보지 않는다.
- 현재 `pgBackRest check`와 WAL 검사를 각각 한 번 실행한다. 해결되지 않은 archive 오류와
  10분 넘게 `.ready` 상태인 WAL을 확인한다.
- 예약 백업이 성공했다면 그 증거를 재사용한다. 누락·실패했다면 원인 해결 후 full backup 1회를 실행한다.
- 기존 복구 시험의 적용 범위를 명시한다. `check` 성공을 새 DB 복구 리허설 완료로 기록하지 않는다.

### 5단계 — 평시 복귀

- 가드를 켠 실행은 성공·오류·중단 여부와 관계없이 즉시 가드 해제·backend 재기동·readiness·HTTPS 복귀를 확인한다.
- 로그아웃·전용 쓰기 정리·비밀 입력 폐기·임시 timer와 수집 프로세스 정리를 확인한다.
- 이 계획된 재기동의 GC·시작 상태를 앞선 정상 점검 구간에 합산하지 않는다.
- 실제 4GiB 설정과 서비스·자동 timer의 최종 상태를 남긴다.

## 3. 판정과 조치

| 관측 결과 | 판정·조치 |
|---|---|
| OOM·의도하지 않은 종료·미복구 서비스 | 실제 장애다. 원인·복구·해당 기능 재확인까지 조치 필요 상태로 둔다 |
| 정상 입력의 잘못된 status·필수 내용·계정 분리 | 기능 또는 데이터 문제다. 원인 해결 후 관련 항목을 재확인한다. RAM 부족으로 자동 분류하지 않는다 |
| 일반 3초·외부 조회 10초·코스/동선 15초 초과 | 기존 최대 대기 목표를 진단 기준으로 재사용한다. 원인·재현 여부·영향을 기록하고 성능 개선 항목으로 남긴다. 단발 초과로 전체 점검을 폐기하지 않는다 |
| 공급자 오류·가드 trip | 호출을 멈추고 가드를 해제한다. 공급자·키·쿼터와 서버 원인을 구분하며 미확인 외부 기능을 성공으로 바꾸지 않는다 |
| 짧은 Full GC·swap 증가·순간 메모리 여유 20% 미만 | GC 정지 시간·회수 후 사용량·실제 요청과 대조할 진단 자료다. 그 값만으로 중단·증설하지 않는다 |
| 백업 누락·실패·WAL 보관 불능 | 데이터 보호 문제다. 원인 해결 후 실제 백업·검사 성공을 확인한다 |
| 로그·계측 부족 | 해당 구간·항목은 미확인이다. 자료 부족을 성공이나 서버 장애로 바꾸지 않는다 |

실제 메모리 문제가 있으면 host RAM·JVM heap·cgroup 상한을 먼저 구분하고 4GiB 안에서 설정·코드·
동시 실행 문제를 해결할 수 있는지 검토한다. 서비스가 계속 불안정해 즉시 복구가 필요하면 이미
검증한 **같은 2b 서버의 8GiB 복구 경로**로 응답을 회복하고 원인과 변경을 보고한다.
일시적 GC·swap 자체는 이 긴급 복구의 근거가 아니다.

## 4. 완료 조건과 최종 보고

**“4GiB 기본 운영 점검 완료”**는 다음을 모두 충족했을 때 기록한다.

- 필요한 기능·서비스·백업 확인을 수행했고 해결되지 않은 서비스 중단·기능/데이터 장애·백업/WAL 문제가 없다.
- 지연 등 개선 항목은 실제 값·재현 여부·영향과 함께 보고한다.
- 필수 점검이 자료 부족·로그인·공급자 문제로 남으면 전체 완료로 선언하지 않는다.
  과거 미수집 메모리 시계열이나 전체 부하 통계는 이번 필수 소량 점검과 구분해 미검증 범위로 남긴다.
- 가드 비활성·평시 서비스 복귀·시험 쓰기와 입력 정리가 확인됐다.
- 실행 시각·사양·배포 버전·요청별 결과·장애 이력·백업/WAL·최종 상태를 evidence에 기록했다.

기본 점검 결과를 API 계획·EC2 실행서·GraphHopper 계약·출시 가이드에 같은 의미로 반영한다.
기존 `capacity-v2` 결과는 소급 수정하지 않으며 기본 운영 확인과 전체 부하 비교 통과를 구분한다.
최종 보고는 **4GiB 설정 / 확인 기간·기능 / 발견 문제·해결 여부 / 백업·가드 / 미검증 범위**로 정리한다.

로그인·숨김 입력·도구 준비 후 실제 점검은 약 **30~60분**을 예상하며 문제 수정 시간은 별도다.
새 24시간 대기는 붙이지 않는다. 사용자 입력은 AWS 로그인과 테스트 계정 2개의 숨김 입력이며
나머지는 에이전트가 수행한다. 계획 작성 후 사용자의 “시작해라” 승인에 따라 실행을 시작했다.
commit·push·PR 생성은 이번 실행 범위에 포함하지 않는다.
