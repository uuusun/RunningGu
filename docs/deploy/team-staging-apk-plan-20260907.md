## 목표와 계정

민지와 건모가 각자 에뮬레이터에 같은 스테이징 서명 APK를 설치하고, 사용자가 지정한
서로 다른 테스트 계정으로 로그인해 동선 생성·러닝코스·저장·복원·편집 등을 시험한다.
PC에 Spring·PostgreSQL·GraphHopper를 설치할 필요 없이 EC2 서비스를 사용한다.
계정 주소 매핑은 이번 사용자 대화를 따르며 비밀번호·토큰·인증 코드는 공개 문서나 로그에 남기지 않는다.
두 계정이 기존 스테이징 DB에 준비됐는지 실제 로그인으로 확인한다. 새 계정을 임의로 만들거나
기존 비밀번호를 바꾸지 않는다. 신규 가입·재설정·탈퇴 시험은 일반 기능 시험 계정의 사용과 분리한다.

## 실행 계획

1. **EC2를 켜기 전에 PR을 정리한다.** 승인된 변경을 develop에 Squash merge하고 선행
   변경을 받은 PR의 CI를 확인한다. #301 → 수정된 #311 순서를 지킨다. #313도 CI·리뷰 후
   반영한다. #303·#304와 #313이 함께 고치는 개인정보 문구의 충돌과 14일 정책을 대조한다.
   기존 미커밋 작업 폴더를 pull하거나 덮어쓰지 않고 별도 작업 폴더를 사용한다.
2. **시험할 통합 커밋을 고정하고 빌드한다.** 최종 develop 커밋, 포함 PR, 미포함 기능을
   기록한다. 백엔드는 성공한 develop push CI의 `runninggu-backend-<SHA>` 묶음과
   `release-manifest.txt`·`SHA256SUMS`를 준비한다. Android는 해당 통합본에서 JDK 21로
   `:app:testDebugUnitTest :app:assembleRelease`를 실행하고 기존 키로 서명한다.
   `API_BASE_URL=https://staging-api.runninggu.store/api/`, 기존 네이티브 키·인증서를 사용한다.
   이 APK를 설치하면 기본 debug의 `10.0.2.2` 설정은 사용되지 않는다.
3. **CI의 경로 필터를 확인한다.** 마지막 머지가 Android/문서만 바꾸면 같은 SHA의 백엔드
   artifact가 생기지 않을 수 있다. 가능한 머지 순서에서 양쪽 CI가 실행되는 통합점을 잡는다
   (예: Android와 API 명세를 함께 바꾸는 #300). 실제 push diff와 CI 결과로 확인한다.
   artifact가 다른 SHA이면 같은 SHA라고 표기하지 않는다. 다른 서버 artifact를 채택해야 할
   경우 그 커밋 이후 백엔드·배포 입력이 동일한지 확인하고 앱/서버 SHA를 각각 명시한다.
   필요한 CI 실행 경로 변경은 앱 코어 담당과 정리하며 검증하지 않은 JAR로 대체하지 않는다.
4. **배포·기기 시험 직전에 4GiB EC2만 켠다.** 상태 검사, PostgreSQL, GraphHopper,
   Spring, Nginx·HTTPS를 확인한다. 배포 전 백업·WAL과 현재 SHA·graph ID를 보존하고
   [실행서 §17](aws-ec2-staging-runbook.md#17-이후-배포)에 따라 새 release·Importer·Flyway·
   서비스 기동·readiness를 확인한다. [4GiB 메모리 기준](evidence/staging-4g-deployment-baseline-20260907.md),
   기존 DB·시크릿·14일 로그 설정을 유지한다. 앱 배포만을 이유로 graph를 재생성하지 않는다.
5. **전달 전에 새 AVD에서 실제 APK를 시험한다.** 서명·staging 주소·권한·R8를 검사하고
   이메일 로그인, 대회/축제/상세, 동선 생성→저장→앱 재시작→복원→편집,
   큐레이션/OSM 러닝코스·지도·코스 저장·찜·마이·프로필/동의 복원을 확인한다.
   두 계정의 저장 결과가 서로 보이지 않는지도 확인한다. 카카오 로그인은 별도 카카오
   계정으로, 가입·재설정은 실제 수신 허용 상태와 메일 도착까지 확인한다.
   실패 항목은 재현 조건과 함께 기록하고 미완료 기능을 정상으로 보고하지 않는다.
6. **팀이 받을 묶음을 전달한다.** APK, SHA256SUMS, 설치 안내, 앱/서버 SHA,
   포함·미포함 기능, 두 계정의 시험 역할, 기기별 기록 틀을 묶는다. 비밀번호·keystore·
   서버 시크릿은 넣지 않는다. 기존 debug 앱과 서명이 다를 수 있으므로 새 AVD 설치를
   기본으로 한다. 두 사람 모두 파일 수신·설치·로그인한 것을 확인해야 전달 완료다.
   비공개 공유 위치는 실행 시 기존 팀 공유 경로를 확인해 사용한다.
7. **테스트 운영 시간을 정한다.** 두 사람이 사용하는 시간에는 4GiB EC2를 유지하고,
   사용 종료를 확인한 뒤 중지해 Stopped를 재확인한다. 정해지지 않은 시각에 임의로
   자동 중지하거나 24시간 상시 기동 승인으로 해석하지 않는다. EBS·고정 IP 등 보유 비용은 별도다.

## 실행 전 남은 선택과 완료 조건

- 정확한 시험 시작/종료 시간과 비공개 APK 전달 위치는 실행할 때 확인한다. PR 정리와
  로컬 빌드 준비를 시작하기 위해 먼저 정할 필요는 없다.
- #311 수정·승인 전에 예비 APK를 전달한다면 저장 후 편집 미포함을 명시해야 한다.
  이번 목표의 전체 기능 시험본 완료와는 구분한다.
- 완료 기준: 선택한 통합 변경 머지·필요 CI 성공 → 배포된 서버 버전과 정상 응답 확인 →
  새 서명 APK의 실제 AVD 시험 → 민지/건모 각 계정 로그인·데이터 분리 → 파일 수신 및 시험 시간 공유.
- 최초 계획 단계에서는 GitHub 읽기와 기존 기록 대조만 수행했다. 후속 통합의 머지 결과와
  실제 CI 결과는 실행 기록에 별도로 남긴다. 기기·실서버 테스트 결과로 대신하지 않는다.
