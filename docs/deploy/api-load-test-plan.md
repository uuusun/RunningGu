# 앱 API 부하 시험 계획 — 기준·요청 세트 승인 완료, PR 준비 중

> 작성·기준 승인: 2026-09-04. 운영책임자가 이 대화에서 §4 요청량·비율·동시성과 §5 합격 기준에
> 동의하고 다음 시험 준비를 승인했다. **전체 실행 준비가 완료되거나 부하를 통과했다는 뜻은 아니다.**
> 첫 계정 가입·재로그인·앱 재시작 후 인증된 GET `/me`를 확인했다. 마케팅 상태 복원 결함 #287은 별도 미해결로 두고 진행한다.
> 테스트 계정 2개 생성과 KTO 최종 키의 소량 재검증은 완료했다. 카카오 실제 사용량은 확인했으며,
> KTO 포털에서는 실시간 당일 사용량·잔여량을 확인할 수 있는 화면을 찾지 못했다. 이를 숫자로
> 추정하지 않고, 계정 간 데이터 분리 실행 확인·승인된 외부 호출 가드와 고정 요청 세트의 PR 검토·배포를 남은 조건으로 둔다.
> 회원 생성·메일 설정 변경·4GiB 변경은 각각 필요한 준비와 별도 승인을 거친다.

## 1. 목적과 기존 검증의 경계

- `HTTPS → Nginx → Spring Boot → PostgreSQL·GraphHopper·외부 API` 경로를 시험한다.
- 기존 [8GiB 증거](evidence/graphhopper-ec2-8g-20260904.md)는 GraphHopper 직접 요청
  60건/분의 결과다. 앱 API 60건/분, 최대 사용자 수 또는 모든 기능의 정상 동작을 증명하지 않는다.
- [#263 머지 후 배포 기록](evidence/staging-develop-b9e632d-20260904.md)의 `develop` CI 묶음을 사용한다.
  이전 #255 배포·GraphHopper 검증 이력은 각 기록에 별도로 보존한다.
  `main` 정식 릴리스나 프로덕션 공개와는 별개다.
- HTTP 계약은 [API 명세](../files/런닝구_API_명세서.md), 화면 사용 경로는
  [화면/API 매핑표](../screen-api-matrix.md)를 따른다. 이 시험 때문에 응답·재시도·캐시·오류 정책을
  바꾸지 않는다. 구현과 명세가 다르면 별도 계약 검토부터 한다.

## 2. 실행 전에 확정할 것

1. **완료:** 운영책임자가 2026-09-04 대화에서 §4 요청량·혼합 비율·동시성, §5 응답시간·실패 기준을 승인했다.
2. 테스트 전용 계정 2개와 생성 데이터의 소유 범위를 지정한다. 실제 사용자 계정·개인 데이터는 쓰지
   않는다. 토큰·비밀번호·이메일은 문서/fixture/로그에 넣지 않고 안전한 비공개 입력으로 전달한다.
3. 실제 KTO·카카오 키의 유효성과 공급자별 한도를 확인하고, 시험 중 허용할 호출 상한을 확정한다.
   값이 환경변수에 있다는 사실만으로 유효하다고 판정하지 않는다. KTO 포털에 표시된 상세 기능별
   일일 한도 1,000을 실시간 잔여량으로 읽지 않으며, 당일 사용량 화면을 찾지 못한 상태에서는
   §4의 더 작은 내부 상한을 실제 HTTP 송신 전에 강제한다. 가드가 없으면 해당 시험은 멈춘다.
4. **완료:** 읽기 전용 사전 요청으로 성공이 확인된 대회·코스·공개 지점·목표거리·생성 조건을
   선정하고, 운영책임자가 2026-09-05 요청 세트 v1을 승인했다. 버전·hash·기대 응답 조건은
   부하 시작 전에 고정하며 비밀값은 세트에서 분리한다.
   앱의 기기 위치 자동 수집이나 위치 권한을 추가하지 않는다.
5. 확정된 계획과 실행 도구를 별도 PR로 검토한다. 새 라이브러리·API·DB 스키마·테스트 인증 우회는
   승인 없이 추가하지 않는다. 기존 Python 표준 라이브러리 기반 도구의 패턴을 우선 검토한다.

앱 API 재검증에서 주소별 204와 실제 두 메일함 도착을 확인했다. 이 메일 수신 시험 자체가 정상 가입 증거는 아니다.
실제 혼합 부하 실행기와 고정 요청 세트는 2026-09-05 로컬 변경으로 작성했고 운영책임자가
요청 세트 v1을 승인했다. 아직 PR 검토·staging 배포·실행은 하지 않았다. 공개 조회 준비 도구나 승인 전 후보의
오프라인 검증을 30분 부하의 대체물로 취급하지 않는다.

[정상 가입 사전 점검](evidence/signup-preflight-20260904.md) 당시 필수 `ageOver14` 누락으로
서버 #263 반영을 요청했다. 이후 사용자가 머지했고 새 `develop` CI 묶음을 staging에 배포해
연령 입력 거부 경로 5개와 공개 조회 7항목 2회가 통과했다. 이로써 해당 차단은 해소됐지만,
전체 혼합 부하는 미실행이다. 사용자 승인 후 공유 코드 변경 없이 기존 release
설정으로 [staging 연결 APK](evidence/android-staging-release-20260904.md)를 빌드·설치했다.
사용자가 직접 가입을 완료했고 [가입 실행 증거](evidence/signup-success-20260904.md)에서 인증 200·가입 201,
회원·약관·첫 세션을 확인했다. 후속 로그아웃·재로그인 성공과 별개로
[마케팅 상태 복원 결함](evidence/marketing-relogin-diagnosis-20260904.md)이 확인됐다. 최초 진단 당시에는 인증된 GET `/me`가 미검증이었다.
자동 동의나 인증 우회는 하지 않는다.

후속 운영책임자가 [#287](https://github.com/uuusun/RunningGu/issues/287) 게시와 해당 결함을 제외한
검증 재개를 요청했다. [읽기 전용 후속 증거](evidence/api-readonly-boundaries-20260904.md)에서
공개·미인증 경계 14항목 2회 동일 통과, 도구 테스트 24개 통과와 앱 재시작 뒤 GET `/me` 200을 확인했다.
위 최초 진단의 GET `/me` 미확인 상태는 해소됐지만 재로그인 직후 마케팅 표시 결함은 미해결이다.
마케팅 스위치 유지 항목만 별도 추적하며 인증·내 정보·소유권·부하 합격 기준은 완화하지 않는다.
같은 후속 증거에서 두 번째 가입 201·회원 2명·인증 identity 2개를 확인했다. 계정 생성과 별개로
부하 생성기는 비공개 인증 입력과 두 계정 데이터 분리·제한된 쓰기 preflight를 구현했다.
다만 승인된 코드가 staging에서 실제 두 계정으로 통과하기 전까지 준비 완료로 판정하지 않는다.

후속 [KTO 승인 확인 기록](evidence/kto-approval-check-20260904.md)에서 개인 계정의 필요한 세 서비스
승인과 표시 한도를 확인했다. 조회 중 인증키가 자동 도구 출력에 포함되어 사용자에게 알리고
재발급을 요청했다. 이후 사용자 재발급·비공개 입력 완료 뒤 EC2의 후보 파일을 사용한 소량 호출
4건이 모두 HTTP 200·정상 코드 `0000`으로 성공했다. 이후 운영책임자 승인으로
`KTO_SERVICE_KEY`만 교체하고 백엔드를 재시작했다. 새 키 적용·다른 설정 보존,
HTTPS 축제·TOUR·WELLNESS·코스 지역·대회 조회 5항목과 두루누비 동기화 성공을 확인했다.
GPX catalog 261개는 유지됐고 임시 후보 키 파일은 삭제했다. 상세 명령 ID·시각·수치는 위 기록을 따른다.
이는 해당 API의 소량 기능 검사이며 앱 전체 기능·혼합 부하·4GiB 합격이 아니다.
KTO 당일 사용량을 포털에서 확인할 수 있다고 전제하지 않으며, 승인된 내부 상한의 실제 시도
계측/차단과 비공개 부하 인증 입력·두 계정 분리 검증은 별도로 완료해야 한다.

2026-09-05 당일 사용량 확인 과정에서 인증키가 표시된 포털 접근성 출력과 echo-off 웹 터미널
접근성 입력 필드에 각각 키가 포함돼 해당 키들을 즉시 재발급했다. 최종 입력 뒤에는 터미널을 자동
판독하지 않았고, 고정된 root 전용 후보 경로를 별도 Run Command가 읽었다. KTO 4개 상세 기능
각 1회 성공 결과 파일을 독립 재검증한 뒤 `KTO_SERVICE_KEY` 한 줄만 원자 교체하고 백엔드만
재시작했다. 외부 HTTPS 5개와 동기화·로그 유출·후보 정리를 다시 확인했다. 상세 실패·명령 ID·
수치는 [KTO 승인 확인 기록](evidence/kto-approval-check-20260904.md)의 2026-09-05 절을 따른다.
보안 재교체 성공이 승인된 내부 상한 집행이나 30분 부하 합격을 대신하지 않는다.

2026-09-05 [후속 준비 기록](evidence/api-load-upstream-preparation-20260905.md)에서
분당 비율을 지키는 오프라인 도착 시간표 2,100건(준비 300 + 본 시험 1,800)을 작성했다.
후속 로컬 변경에서 성공 입력 fixture와 혼합 부하 실행기, 계정 분리·갱신·정리·합격 요약을
추가하고 API 도구 테스트 46개를 통과했다. 운영책임자가 승인한 fixture는 `APPROVED`로 고정했지만,
이는 PR 검토·staging 배포나 부하 실행의 증거가 아니다.
후속 카카오 관리 콘솔 확인에서 호출 이력이 staging 점검과 일치하는 앱의 월간·일간·유료
사용량을 확인하고 EC2 앱 ID도 직접 대조했다. 기존 429 재시도 때문에 앱 200만으로 첫 upstream
429를 감지할 수 없다는 관측 공백을 메우는 staging 가드도 로컬에서 구현·단위 검증했지만 아직
PR·배포 전이다. 외부 시도별 계측·허용 상한이 실제 staging에서 확인되기 전에는 전체 부하를 시작하지 않는다.

## 3. 전체 기능 확인과 반복 부하를 분리한다

### 3.1 엔드포인트별 기능 스모크

P0 구현 API의 정상 흐름과 필요한 오류 흐름을 계약대로 소량 확인한다. 그룹 단위 요약만 남기지
않고 실행 전 method·경로별 체크리스트와 예상 status·응답 검증을 고정한다.

| 그룹 | 범위 | 실행 경계 |
|---|---|---|
| 조회 | 대회 목록·상세·일별 집계·마감 임박, 축제, 코스 목록·지역 | 실제 snapshot·catalog 및 외부 응답 확인 |
| 검색·추천 | 주변 코스, POI, 지오코딩, 동선 생성 | curated 경로와 OSM 생성 경로 구분, 외부 호출 상한 적용 |
| 인증 | 중복 확인, 이메일 인증·가입·로그인·갱신·로그아웃, 카카오 인증 | 메일·카카오의 별도 준비 후 실행; 발송 반복 부하 제외 |
| 회원 | 내 정보·프로필·약관·재인증·비밀번호·탈퇴 | 전용 계정만; 탈퇴는 폐기 승인된 계정에 한 번 |
| 저장 | 즐겨찾기, 저장 코스, 저장 동선·블록 편집·정렬 | 생성한 ID allowlist만 수정·삭제; 다른 계정 접근 거부도 확인 |
| 복구·오류 | 계약에 정해진 인증 실패·입력 오류·빈 결과·외부 장애 처리 | 정상 부하와 분리해 기록; 정상 성공률에 합산하지 않음 |

API 명세에서 P1 예약인 directions 등 미구현·범위 밖 기능을 P0 완료 조건에 추가하지 않는다.
카카오 실제 로그인처럼 사람의 동의가 필요한 흐름은 사용자 입력 없이 우회하지 않는다.

### 3.2 반복 부하 대상

메일 발송·가입·비밀번호 재설정·탈퇴·카카오 로그인은 반복하지 않는다.
인증 부하는 사전 로그인한 전용 계정의 토큰으로 내 정보·즐겨찾기를 사용한다.
Access token 유효기간 30분을 고려해 준비·warm-up 시간을 포함하여 기존 refresh 계약으로 갱신한다.
갱신 요청·실패는 별도 집계하며 1,800개 본 요청에 숨기거나 실패를 제외하지 않는다.
인증 rate limit을 해제하거나 우회하지 않는다.

## 4. 1차 부하 프로파일 — 운영책임자 승인

이 수치는 실제 이용량 추정이나 최대 수용 인원이 아니라 **첫 비교 시험용 입력**이다.

- EC2 밖의 부하 생성기에서 staging HTTPS 주소를 호출한다. 생성기 CPU·네트워크 포화도 기록한다.
- warm-up 5분 후 본 시험 30분. 본 시험은 **60 API 요청/분, 최대 동시 진행 4개**, 총 1,800건.
- 요청 도착 시각을 미리 고정한다. 느려졌다고 다음 요청 시각을 늦추지 않는다.
  동시성 한도 때문에 예정 시각에 시작할 수 없으면 `missed start`로 기록해 실패한다.
- 아래 비율을 분마다 유지하도록 서로 섞어 예약한다. 세션/화면 수가 아니라 **HTTP 요청 수**다.

| 그룹 | 요청/분 | 비율 | 입력 구성 |
|---|---:|---:|---|
| 대회 조회 | 30 | 50% | 목록 12, 상세 8, 마감 임박 5, 일별 집계 5 |
| 코스 목록·지역 | 9 | 15% | 목록 6, 지역 3 |
| 주변 코스 | 6 | 10% | curated 결과가 있는 입력 3, OSM 생성을 타는 입력 3 |
| 외부 조회 | 6 | 10% | 축제 2, POI 2, 지오코딩 2 |
| 동선 생성 | 3 | 5% | 계약상 유효한 고정 대회·일정·테마 조합 |
| 인증 조회·제한된 쓰기 | 6 | 10% | 내 정보 2, 즐겨찾기 목록 2, 전용 즐겨찾기 추가 1·삭제 1 |
| **합계** | **60** | **100%** | 본 시험 30분 = 1,800건 |

즐겨찾기 추가·삭제는 같은 전용 계정·시험 대상으로 순서를 지키되, 선행 요청이 실패하면 후속 요청을
성공처럼 세지 않는다. 고정 도착률을 지키지 못한 경우도 실패다. 생성한 쓰기 대상과 원래 존재하던
대상을 구분해 원래 데이터를 정리 대상으로 삼지 않는다.

### GraphHopper 요청 수와 같지 않은 이유

현재 `/courses/near`는 curated 경로가 없을 때 OSM 후보를 생성한다. OSM 생성기는 최대 16개
seed를 순차 호출하지만 외부 오류 시 중단할 수 있다. **OSM 입력 3건/분은 GH 직접 요청 최대
48건/분의 상한 계산일 뿐, 실제 48건을 수행했다는 증거가 아니다.** 실제 호출·성공·실패·중단을
따로 집계한다. 주변 코스에는 걷기 스팟 외부 조회도 포함된다.

이 혼합 시험이 기존 GH 직접 요청 60건/분 시험을 대체하지 않는다. 앱 부하와 기존 GH 부하를
동시에 추가해 합계 부하를 몰래 높이지도 않는다. 더 높은 OSM 비율·요청량 탐색은 별도 승인한다.

### 캐시·외부 API

- 기존 캐시 정책을 유지한다. 준비·warm-up·본 시험을 나눠 기록하고 cache hit/miss 또는 실제
  upstream 호출 관측 근거를 남긴다. 관측이 불가능하면 그 한계를 적고 외부 부하 합격을 주장하지 않는다.
- 반복 입력의 warm-cache 결과만으로 처음 조회하는 지점·검색어 성능을 주장하지 않는다.
- cold 입력은 별도 소량 시나리오로 사전 고정한다. 공급자별 허용 호출 상한을 먼저 정하고
  본 시험·cold 시험을 합쳐 관리한다. 무작위 검색어·좌표를 대량 생성하지 않는다.
- 실제 upstream 429/5xx/timeout 또는 사전 호출 상한 도달 시 해당 시험을 중단하고 원인을 기록한다.
  기존 계약 외 재시도·가짜 성공 응답·무단 key 교체로 통과시키지 않는다.

### 4.1 staging 외부 호출 가드 — 운영책임자 승인(2026-09-05)

이 가드는 앱 API 부하 시험의 실제 upstream 시도를 계측하고 쿼터를 보호하는 **staging 전용 시험
장치**다. 제품 HTTP API, 캐시, 원천 우선순위, 재시도·페이지·폴백, 오류 응답 계약을 변경하지
않는다. 기본값은 비활성이며 production에서는 활성화하지 않는다.

| 환경변수 | 비활성 기본값 | 승인된 시험 값 |
|---|---:|---:|
| `RUNNINGGU_DEPLOYMENT_ENVIRONMENT` | `local` | `staging` |
| `UPSTREAM_LOAD_GUARD_ENABLED` | `false` | `true` |
| `UPSTREAM_LOAD_GUARD_RUN_ID` | 빈 값 | 영숫자·`.`·`_`·`-`만 사용한 1~64자 고유 ID |
| `UPSTREAM_LOAD_GUARD_KTO_ENDPOINT_LIMIT` | `0` | `100` |
| `UPSTREAM_LOAD_GUARD_KAKAO_TOTAL_LIMIT` | `0` | `5000` |
| `UPSTREAM_LOAD_GUARD_KAKAO_ENDPOINT_LIMIT` | `0` | `2000` |

- 활성화 시 배포 환경이 정확히 `staging`이어야 한다. run ID와 세 상한을 모두 명시하며 환경 불일치,
  누락·0·음수·잘못된 run ID 또는 승인 최대값(100·5,000·2,000) 초과면 서버 기동을 거부한다.
- 실제 네트워크 송신 직전에 시도 1건을 원자적으로 예약한다. 재시도, 페이지 추가 조회, 1순위 실패
  뒤 폴백도 각각 센다. cache hit은 세지 않는다.
- KTO 허용 operation은 `KorService2/searchFestival2`, `KorService2/locationBasedList2`,
  `WellnessTursmService/locationBasedList`, `Durunubi/courseList`이며 **operation별 100회**가 상한이다.
- 카카오 허용 endpoint는 `/v2/local/search/keyword.json`, `/v2/local/search/category.json`,
  `/v1/user/access_token_info`, `/v2/user/me`이며 **전체 5,000회와 endpoint별 2,000회**를 함께 적용한다.
- 상한의 N+1번째 시도와 allowlist 밖 KTO·카카오 경로는 네트워크 송신 전에 차단하고 전체 run을
  실패 상태로 전환한다.
- 첫 upstream `429`, 예상 밖 `5xx`, timeout 또는 누락을 포함한 KTO `resultCode != 0000`에서 전체
  run을 즉시 실패 상태로 전환하고, 해당 시도에서 고정된 guard 예외를 던져 앱 요청과 부하 생성기를
  실패시킨다. staging 시험 중에는 이 예외를 기존 provider 폴백으로 숨기지 않는다. 이미 송신된 동시
  요청을 취소하지는 않으며, guard 비활성 상태의 제품 오류·폴백 계약은 바꾸지 않는다.
- 한 번 실패한 run은 같은 run ID에서 복구하지 않는다. 백엔드 재시작으로 counter를 초기화해
  시험을 이어가지 않으며, 본 시험 중 재시작 자체도 정상 부하 실패다.
- 로그·결과에는 run ID, provider, 고정 operation/endpoint ID, 시도 수·상한, 결과 class,
  elapsed만 남긴다. URI, query, header, body, 예외 원문과 API 키·토큰·이메일·좌표는 남기지 않는다.
- 시험 종료 뒤 가드를 다시 비활성화하고 재기동한 뒤 비활성 상태를 확인한다.

상한 N+1 선차단, 재시도·페이지·폴백의 개별 집계, `429`·`5xx`·timeout·KTO 오류 trip은 실제
공급자에 고의 오류를 만들지 않고 mock server와 단위·통합 테스트로 증명한다. 가드 구현·테스트·
staging 배포가 끝나기 전에는 30분 혼합 부하를 시작하지 않는다.

## 5. 합격 기준 — 운영책임자 승인

### 5.1 정상 앱 API 부하

| 항목 | 승인된 1차 시험 기준 |
|---|---|
| 부하 유지 | 예정 1,800건 모두 시작·완료, missed start 0; 추가 인증 갱신도 별도 모두 정상 |
| HTTP·내용 | 각 고정 요청의 계약상 기대 status·응답 구조·필수 내용 일치. 예상 밖 4xx·5xx·timeout·연결 오류 0 |
| 단순 조회·인증·즐겨찾기 쓰기 | 그룹별 p95 ≤ 1초, 최대 3초 |
| 외부 조회 | 그룹별 p95 ≤ 3초, 최대 10초 |
| 주변 코스·동선 생성 | curated/OSM/생성 각각 p95 ≤ 5초, 최대 15초 |
| 데이터 | 다른 계정 데이터 노출·의도하지 않은 변경 0. 쓰기 후 읽기와 소유권 검사 통과 |
| 외부 호출 가드 | 성공 run에서 trip 0, allowlist 밖 시도 0. KTO operation별 ≤100, 카카오 전체 ≤5,000·endpoint별 ≤2,000. 최종 counter와 실제 시도 집계가 일치하고 로그의 키·토큰·이메일·좌표 0 |
| 결과 기록 | 그룹별 예정/완료/성공/실패·p50/p95/max, 실패 원인·degraded·빈 결과 수를 각각 기록 |

위 API 전체 응답시간은 기존 GH **직접 요청 하나의 read timeout 5초**에서 유도한 값이 아니다.
사용자 대기시간을 위한 이번 시험 기준이다. 부하 생성기의 판정에만 적용하고 제품의 client/server
timeout 설정을 변경하지 않는다. 계약 문서와 실행 도구는 실행 전 PR 검토 대상이다.
실패 응답을 percentile 계산에서 숨기지 않고 실패율과 시간 분포를 함께 보고한다.

`no valid point` 400은 GH 개별 요청 실패다. OOM으로 세지 않는다고 성공이 되지 않는다.
앱이 계약에 따라 `200 + degraded`나 일부 결과를 반환해도 그 사실을 별도 기록한다.
**정상 고정 입력의 기대 품질이 낮아지면 용량 시험은 실패**로 판정하며, 제품의 HTTP 계약을 바꾸지 않는다.
예상된 빈 결과·degraded·의도적 400은 별도 기능/오류 스모크 대상으로 두고 정상 부하 성공 건수를
채우는 입력으로 사용하지 않는다. 실패 입력을 관측 후 빼서 세트를 다시 맞추지 않는다.

### 5.2 자원·복구

[기존 artifact 계약 §9](graphhopper-artifact-contract.md#9-사전-합격-기준)의 기준을 완화하지 않는다.

- 5초 표본마다 host `MemAvailable` ≥ 전체 RAM의 20%, 정상 OOM 0, 비정상 재시작 0.
- warm-up 후 swap 사용 증가·지속 swap-in/out 없음, readiness 이후 반복 Full GC 없음.
- 본 시험 중 전체 백업 1회, WAL 점검 3회 성공. 부하 때문에 백업을 빼지 않는다.
- JVM heap뿐 아니라 GH cgroup·Spring systemd·PG·호스트 수치를 함께 기록한다.
- GH 직접 요청 검증·장애 격리·재부팅은 기존 계약대로 별도 증거를 유지한다.
  의도적 OOM은 정상 부하 시간대와 분리한다.

정상 부하 실패를 RAM 부족으로 바로 단정하지 않는다. 인증/fixture, upstream, DB 쿼리,
GraphHopper 품질, 부하 생성기 포화, 실제 메모리 부족을 증거로 분류한 뒤 재시험한다.
기준이나 요청량을 결과에 맞춰 낮춘 재시험은 동일 조건 합격이 아니다.

## 6. 승인 이후 작업 순서

1. 로컬에서 작성한 문서·실행 도구·staging 외부 호출 가드를 PR로 검토한다. 전체 backend 테스트와
   기본 비활성 상태를 확인하고, 테스트 환경과 비밀값 입력 경로를 고정한다.
2. method·경로별 스모크를 실행한다. 실제 외부 연동·메일 등 미완료 항목을 남긴 채 전체 통과로 표시하지 않는다.
3. **완료(2026-09-05):** 고정 성공 요청 세트·기대 내용·upstream 허용량을 승인하고
   정규화된 JSON 내용의 canonical SHA-256을 남겼다.
4. EC2의 현재 버전·이미지·graph·설정·기존 백업/복구 경로를 대조한다.
5. 명시적 run ID와 승인 상한으로 staging 가드를 활성화하고, preflight에서 설정·allowlist·counter
   초기 상태와 실제 송신 전 차단 경계를 확인한다.
6. 8GiB에서 warm-up → 30분 혼합 부하 + 백업·WAL + 5초 관측을 실행한다.
7. 시험 직후 가드를 비활성화하고 백엔드를 재기동해 평상시 동작으로 복귀했는지 확인한다.
8. API 그룹별 결과와 자원 결과를 각각 판정하고 실패 원인·미검증 범위를 보고한다.
9. 8GiB 통과 후에만 4GiB 시험 여부를 사용자에게 확인한다. 가능 인스턴스/비용·CPU 차이도 확인한다.
10. 4GiB를 승인하면 heap·상한 후보를 별도 정하고 같은 입력·도착률·동시성을 유지한다.
   기존 계약의 전체 시나리오 3회 연속 통과와 동일 앱 부하 비교가 모두 필요하다.
   hard limit 조합이 바뀌면 별도 장애 격리도 재검증한다. 실패하면 검증된 8GiB·설정으로 복구한다.
11. 결과로 사양·제한을 확정한다. 검증 종료 후 EC2 중지 여부는 운영 일정과 함께 확인한다.

현재 단계에서 앱 부하 합격, 4GiB 운영 가능, 최소 RAM 또는 최대 동시 사용자 수는 아직 결론 내릴 수 없다.
