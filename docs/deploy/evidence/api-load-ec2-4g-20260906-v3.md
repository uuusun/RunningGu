## 자원·GC 관측의 범위

EC2의 40분·5초 계측은 시작하지 않았다. 최저 MemAvailable·CPU·swap-in/out 추세와
API 지연의 동시 상관을 만들 수 없다. 사전 단일 상태의 MemAvailable은 27.866%, swap 사용 52KiB다.
이 값은 부하 최저값이나 40분 추세가 아니다.
08:04:55 단일 상태는 MemAvailable 1,149,484KiB, swap 사용 52KiB,
누적 pswpin 0/pswpout 16이다. counter의 시작 표본이 없으므로 run의 swap-in/out 증분으로 쓰지 않는다.

백엔드 journal에는 다음 시작 GC가 있었다. 모든 Full GC 원인은 `Metadata GC Threshold`였고,
아래 두 묶음은 각각 readiness 이전·가드 해제 후 계획 재기동이다. 정상 앱 부하 구간은 존재하지 않는다.

| 구간 | 모든 pause | 누적 pause | Full GC | Full GC 정지(ms) | Full GC 후 heap(MiB) |
|---|---:|---:|---:|---|---|
| 가드 활성화 후 readiness 이전 | 18 | 325.999ms | 3 | 25.236 / 66.930 / 51.519 | 10 / 18 / 25 (heap 247MiB) |
| 가드 해제 후 계획 재기동 | 19 | 414.487ms | 4 | 25.488 / 50.302 / 60.041 / 104.711 | 10 / 18 / 25 / 45 (heap 247MiB) |

각 GC의 원인·UTC·전후 heap은 서버 원본 JSON에 모두 남겼다. GC 횟수를 탈락 조건으로 사용하지 않았다.
조회 구간의 JVM/커널 OOM 지표는 0, backend NRestarts 0, GH/PG restart count 0이다.
backend InvocationID 변경은 가드 ON/OFF에 따른 계획 재기동 두 번이며 비정상 재시작이 아니다.

PC NIC는 준비 중 32표본만 수집했다(07:47:48~07:50:23 UTC).
이 구간 송신 최대 0.408950%, 수신 최대 1.285587%, 오류·discard counter 증가 0,
link down·counter reset 0이었다. 이는 전체 부하 송신 품질 증거가 아니다.

초기 증거만으로는 첫 호출 시도의 timeout 단계가 구분되지 않았다. 이후 사용자 요청에 따른
[후속 조사](kto-tls-diagnosis-20260906.md)에서 DNS·TCP 성공 뒤 `apis.data.go.kr`의 TLS 응답이
오지 않는 현상을 EC2와 PC에서 재현했다. Java 21·TLS 1.2/1.3에서도 동일했다.
최초 07:47 사건은 가드가 원래 예외를 보존하지 않아 TLS였다고 소급 확정할 수 없다.
07:49:54에는 동일 설정으로 두루누비 동기화가 832ms에 성공한 기록도 확인했다.
후속 조사는 부하 재시도가 아니며 가드 재활성화 없이 진행했고, TLS에서 실패해 HTTP 송신은 0회였다.
