카카오 실제 송신은 이 preflight에서 발생하지 않았다. 이는 승인된 실행서의 필수 KTO 송신 계측
검사이며, 카카오 실제 혼합 부하 통과를 주장하지 않는다.

숨김 입력 완료 신호가 없어서 시작 게이트를 만들지 않았다. 로컬 `started.json`과
`start-authorized.json`이 모두 없음을 확인했고, 이번 작업에서 연 입력 프로세스만 종료해
메모리에 남았을 수 있는 값을 폐기했다. 로그인·두 계정 preflight·반복 요청은 보내지 않았다.
본 시험용 40분 자원·NIC 수집과 시험 중 backup 1회·WAL 3회도 시작하지 않았다.
배포 직전 backup·WAL을 본 시험 실적으로 합산하지 않는다.

**2026-09-05T05:26:38.974401Z**에 가드 해제 후 실제 프로세스의
`enabled=false`, 빈 run ID, 상한 `0/0/0`과 readiness를 확인했다. backend `NRestarts=0`이며
외부 HTTPS 동일 7항목도 다시 통과했다. 타임아웃 해제용 임시 timer의
`LoadState=not-found`, `ActiveState=inactive`와 backend·GraphHopper `active`를 최종 확인했다.
`05:12:00 UTC` 이후 backend journal에서 현재 KTO·카카오 REST·JWT·SMTP username/password
5개 비밀값의 원문 일치는 0건이었다. 원문은 메모리에서만 대조했으며 모든 시크릿·모든 로그 저장소의 전수 검사를 뜻하지 않는다.

**첫 준비 run의 판정은 부하 미실행이다.** 예정/실제 전송/완료 2,100건, 본 시험 성공 1,800건,
dispatch 지연·응답시간·메모리·swap·GC·본 시험 backup/WAL 조건은 아직 판정할 수 없다.
가드를 재기동했으므로 이 run ID를 재사용하지 않는다. 기존 테스트 계정 2개의 숨김 입력이
준비되면 **새 run ID**로 가드 활성화·preflight부터 재개한다. fixture·schedule·부하 기준은 유지한다.
8GiB 앱 부하 합격 전에는 4GiB 시험이나 사양 변경을 하지 않는다.

문서 상태를 이번 배포·preflight·미실행 상태로 갱신했다. 제품 API·DB 스키마·공유 실행기 코드는
변경하지 않았고 commit·push·PR 생성은 하지 않았다. 문서의 `git diff --check`는 통과했다.

#### GC 구간 판정

초기 조정기 `gcOom.backendFullGc=10`은 가드 활성화부터 수집 종료까지 `Pause Full|Full GC`에
일치한 **로그 줄 수**다. 시작·완료 두 줄을 한 사건으로 묶으면 실제 사건은 5회다.
원본 집계값을 삭제하거나 0으로 덮어쓰지 않고 `gcReview`의 GC ID·시각·원인을 별도 보존했다.

| 구간 | GC ID | 원인 | 완료(UTC) | 정지(ms) |
|---|---:|---|---|---:|
| 자원 수집·부하 전 | 3 | Metadata GC Threshold | `05:42:08.232` | 25.205 |
| 자원 수집·부하 전 | 6 | Metadata GC Threshold | `05:42:10.028` | 55.788 |
| 자원 수집·부하 전 | 10 | Metadata GC Threshold | `05:42:11.992` | 54.015 |

Spring 애플리케이션의 `Started` 로그는 `05:42:15.844Z`, 자원 수집 시작은 `05:43:06.732762Z`,
외부 실행기 시작은 `05:44:37.816809Z`다. `Started` 로그를 외부 readiness 확인 완료 시각으로 대체하지 않는다.
`gcReview.startupCompletedEvents=4`는 이 조정기의 **자원 수집 전 사건 수**를 뜻한다.
실제 관측 구간의 backend Full GC는 단발 1회, GraphHopper Full GC는 0회였고 반복 발생은 없었다.
계획 §5와 실행서 §15.1의 기준은 “readiness 이후 반복 Full GC 없음”이다. 관측 중 단발 1회를
명시한 상태에서 이 기준을 통과로 판정한다. Full GC가 전혀 없었던 실행으로 보고하지 않는다.
두 JVM 모두 실제 시작 인자의 unified GC logging 활성화를 확인했다. RAM 부족이나 최소 RAM을
이 로그만으로 추정하지 않으며 코드 캐시·GC 설정도 결과에 맞춰 바꾸지 않았다.

## 최종 판정과 미검증 범위

**승인된 동일 fixture·schedule의 8GiB 앱 API 혼합 부하 조건을 통과했다.** 분당 60건·최대 동시 진행 4,
warm-up 300건과 본 시험 1,800건, 정해진 기능·소유권·정리·성능 기준과 40분 자원 관측에 대한 결과다.
관측 중 단발 Full GC 1회를 위와 같이 함께 보고한다. 고정 입력의 캐시 포함 결과를 처음 조회하는
모든 지점·검색어, 최대 동시 사용자 수, 최소 RAM, 프로덕션 공개 승인으로 확대하지 않는다.

기존 GraphHopper graph artifact·8GiB 사양을 유지했다. 4GiB 변경·시험은 수행하지 않았고,
사용자에게 이번 결과를 보고한 뒤 진행 여부를 별도로 확인한다. 마케팅 유지 결함 #287은 시험 범위에서 제외했다.
공유 실행기·제품 API·DB 계약은 변경하지 않았다. 문서와 안전한 증거 파일을 갱신했다.
최종 API·서버·NIC JSON의 요청 수·가드 해제·자원·backup/WAL 조건을 다시 대조했고 모두 일치했다.
문서의 `git diff --check`도 통과했다. 새로 수정한 내용은 문서와 증거 파일뿐이므로 추가 제품 빌드는 실행하지 않았다.
