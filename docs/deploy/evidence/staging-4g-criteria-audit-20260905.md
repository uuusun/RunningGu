# 4GiB 검증 조건 전체 점검 — 2026-09-05

> 후속 요청에 따른 [4GiB 기본 운영 점검 마무리 계획](../staging-4g-closeout-plan.md)을 2026-09-06 작성했다.
> 이후 사용자 승인으로 [기본 운영 점검을 완료](staging-4g-closeout-20260906.md)했다.
> 아래 표는 기존 전체 부하의 조건 감사 이력이며 현재 기본 운영 점검의 판정과 구분한다.

이 문서는 Full GC 2회 때문에 시험이 중단된 뒤 요청받은 조건 전체 점검이다.
현재 `capacity-v2` 문서와 실행기의 판정을 대조한 결과이며, 새 합격 기준의 승인이나
기존 미완료 시험의 소급 합격을 뜻하지 않는다. 서버 설정과 시험 실행기는 변경하지 않았다.

## 1. 앱 API 시험에 적용되는 조건

| 항목 | 현재 조건 | 구분과 검토 사항 |
|---|---|---|
| 부하량 | warm-up 5분 + 본 시험 30분, 60요청/분, 최대 동시 진행 4개. 예정·송신·완료 2,100건, 본 시험 성공 1,800건 | 8GiB와 비교하기 위한 고정 입력이다. 하루 방문 20회에서 계산한 예상 부하는 아니다 |
| 요청 시작 | missedStarts 0, lateDispatches 0, 최대 송신 지연 500ms 이하 | 시험 PC 문제와 서버 처리 지연을 구분한다. 미달 자체로 RAM 부족이 증명되지는 않는다 |
| 단순 조회·인증·즐겨찾기 | 각 그룹 p95 1초 이하, 최대 3초 이하 | 최대값은 한 요청만 초과해도 불합격이다 |
| 외부 조회 | 그룹 p95 3초 이하, 최대 10초 이하 | 공급자 지연과 자체 서버 지연을 구분한다 |
| 주변 코스·동선 생성 | 그룹 및 curated·OSM·생성 각각 p95 5초 이하, 최대 15초 이하 | 합산 평균만 좋다고 합격하지 않는다 |
| 요청 오류 | 예상 밖 4xx·5xx·timeout·연결 오류 0 | 요청 오류는 기록하되 인증·입력·공급자·서버 원인을 분리한다 |
| 응답 품질 | 기대 status·구조·필수 내용 일치, 정상 입력의 예상 밖 빈 결과·degraded 없음 | HTTP 200만으로 성공을 세지 않는 기능 정확성 조건이다 |
| 인증·정리 | preflight 14종, 토큰 갱신 4건, 시험 쓰기 정리·로그아웃 성공 | 준비·정리 실패와 서버 용량 실패를 구분한다 |
| 데이터·비밀정보 | 다른 계정 데이터 노출·의도하지 않은 변경·민감정보 로그 0 | 완화할 성능 지표가 아니다 |
| 가드 | 활성화와 preflight 필수. KTO operation별 100, 카카오 전체 5,000·endpoint별 2,000 이하. TRIP/BLOCK·non2xxResults 0, 실제 송신 counter와 최종 집계 일치 | 쿼터 보호·검증 조건이다. 공급자 장애를 4GiB 부족으로 분류하지 않는다 |
| 외부 오류 발생 시 | 첫 upstream 429·예상 밖 5xx·timeout·KTO 비정상 resultCode에서 가드가 run을 실패 처리하고 후속 호출을 차단 | 현재는 일시적 공급자 오류 한 번도 전체 run 실패다. 서버 사양 판정과 분리할 필요가 있다 |
| 메모리 | 모든 5초 표본에서 MemAvailable 20% 이상 | 한 표본이 19.9%여도 불합격이다. 순간 하락만으로 운영 불가를 단정하는 조건은 재검토 대상이다 |
| OOM·재시작·상태 | 정상 부하 OOM·비정상 재시작 0, 수집 구간의 서비스·컨테이너 정상 실행 | 실제 서비스 중단 지표다. 계획된 재기동 구간은 정상 부하와 분리해야 한다 |
| GC | readiness 이후 반복 Full GC 없음 | 해당 합격표에는 반복의 시간 창·정지 시간·GC 시간 비율이 없다. 이번에는 완료 2회를 반복으로 해석해 중단했다. 횟수만의 탈락 조건은 재검토 대상이다 |
| swap | 사용량·입출력 증분·발생 구간 기록, 증가만으로 중단하지 않음 | 현재는 진단 지표다. 지속 활동을 같은 시각의 성능·메모리·GC와 대조한다 |
| 백업·WAL | 부하 중 full backup 1회, WAL 검사 3회 모두 성공 | 데이터 보호·운영 기능 조건이다 |
| 자원 기록 | 40분·5초 간격 480개 표본 및 각 표본의 필수 서비스·컨테이너 관측 완전성. 누락·파싱 오류·음수 swap 값·누적 counter 감소 없음 | 하나라도 문제가 있으면 요약기가 불합격한다. 계측 불완전과 서버 장애는 별도 판정이 필요하다 |
| 시험 종료 | 성공·실패와 관계없이 가드 해제·백엔드 재기동·readiness·HTTPS 복귀 | 시험 후 평시 복귀 조건이다 |

p95는 요청 95%의 응답시간이 해당 값 이하라는 뜻이다. CPU 사용률, NIC 사용률, PSI는
관측 대상이며 별도 수치 하나로 탈락시키는 합의된 기준은 없다. 특히 PSI `1%·3분`은 적용하지 않는다.

## 2. 앱 API 이후에 남은 조건

- GraphHopper 직접 부하: 고정 입력·고정 도착률로 30분. missed start와 실패 요청 0,
  모든 정상 요청 HTTP 200·비어 있지 않은 paths, client read timeout 5초 이내.
  p50·p95·최대값은 기록하지만 별도의 총 3초 기준은 없다.
- 라우팅 회귀: 기존 기준선의 성공 요청과 합격 지점·거리 셀 및 거리·상승·차도·회전 품질을 유지한다.
  `no valid point`는 요청 실패로 기록하지만 그 자체를 OOM이나 RAM 부족으로 분류하지 않는다.
- 기존 graph artifact 재사용과 run 프로파일을 확인한다. 서버에서 graph를 다시 import하지 않는다.
- 재부팅: GraphHopper unit activation 시작부터 검증을 포함해 GraphHopper·백엔드 readiness 120초 이내.
- Importer: 백엔드를 중지한 별도 구간에서 실행한 뒤 정상 재기동한다.
- 장애 격리: 같은 hard limit의 기존 증거는 재사용한다. 상한 변경 시 GraphHopper만 의도적으로
  OOM시켜 시작 시도 10분 내 3회 제한·알림·PostgreSQL 생존·백업/WAL·동일 graph 복구를 재검증한다.
- 전체 시나리오 3회 연속 통과 뒤 24시간 낮은 활동 상태에서 자동 백업·메모리·서비스·유휴 후 첫 요청을 관찰한다.

## 3. 다음 기준을 정할 때의 검토 방향

이번 문제는 swap 조건만 고치고 나머지 단독 탈락 조건을 함께 검토하지 않은 데 있다.
현재 사용자의 목표는 초기 저활동 서비스의 4GiB 운영 가능성 판단이다.
다음 기준은 아래를 분리해 확정해야 한다.

1. 실제 장애·보호 조건: OOM, 서비스 비정상 종료, 데이터 손상·노출, 백업/복구 실패, 쿼터 보호.
2. 사용자 성능 조건: 정상 응답 비율과 API별 지연. 요청 한 건의 최대값 초과를 어떻게 다룰지 명시한다.
3. 진단 조건: Full GC 횟수·정지 시간·시간 비율·GC 후 메모리 추세, 순간 메모리 여유, swap 활동.
   실제 응답 성능과 장기 안정성을 함께 보고, 관측값 하나만으로 RAM 부족을 단정하지 않는다.
4. 시험 성립 조건: 시험 PC의 전송 지연, 계측 누락, 인증·fixture 준비 오류, 공급자 오류를 따로 분류한다.

Full GC는 G1의 메모리 회수 압력과 정지 시간을 조사할 근거다. 공식 문서도 GC 로그의 원인과
지연·처리량을 분석하도록 설명한다. 이 문서는 새로운 허용 횟수나 임의의 시간·비율 상한을 도입하지 않는다.

## 4. 2026-09-06 — 4GiB 사용과 시험 합격의 구분

사용자는 복잡한 합격표 자체의 충족보다 기존 서버를 4GiB로 설정해 사용하는 것이 목적임을
다시 밝혔다. 기존 staging을 4GiB로 유지하는 것과 `capacity-v2` 전체 시험을 통과했다고
판정하는 것은 별개다. 이 표는 AWS가 요구하는 RAM별 안전 인증이나 사용 허가 조건이 아니라,
프로젝트가 정한 성능·기능·보호·계측 조건을 묶은 비교 시험 기준이다.

API 응답시간·기능 정확성·백업·보안·계측 조건은 RAM 크기와 무관한 목표이고,
OOM·메모리 여유·GC·swap은 메모리 적합성을 분석하는 지표다. 특정 횟수·비율 하나가
운영 안전과 위험을 가르는 보편적인 경계라는 의미는 아니다. 전체 시나리오 3회 연속은
4GiB 추가 검증 조건이며, 8GiB와 모든 절차가 동일했던 것도 아니다.

| 실제 관측 | 8GiB 앱 API 시험 | 4GiB capacity-v2 앱 API 시험 |
|---|---|---|
| 완료 | 2,100건 전부 성공 | GC 판정으로 운영자가 중도 종료 |
| 최소 MemAvailable | 67.372% | 관측 구간 27.383% |
| 정상 부하 OOM·비정상 재시작 | 0 | 관측 구간 0 |
| GraphHopper Full GC | 0 | 2회, 32.152ms·36.316ms |
| 백엔드 Full GC | 관측 중 1회, CodeCache GC Threshold, 123.752ms | 원래 프로세스의 정상 부하 구간 0 |

8GiB는 당시 공통 기준을 통과했지만 GC가 전혀 없었던 것이 아니다. 4GiB의 중단은
서버가 스스로 멈춘 사건이 아니며, 남은 부하·응답시간의 검증을 완료하지 못한 상태다.
방문 20회/일과 API 요청 60회/분은 단위가 다르고, 후자는 전자에서 계산한 예상 부하가 아니다.

마지막 원격 확인인 2026-09-05 13:00Z에 기존 2b 인스턴스는 `c7i-flex.large` 4GiB,
가드 비활성·서비스 정상 상태였다. 8GiB로 되돌리지 않았다. 2026-09-06에는 AWS 콘솔 세션이
만료되어 인스턴스 상태를 새로 조회하지 못했으나, 외부 HTTPS의 `GET /api/contests?size=1`은
인증서 검증을 유지한 상태로 HTTP 200·JSON 응답을 약 0.296초에 반환했다. 이 단일 요청은
현재 공개 API 응답 확인이며 장기 부하 시험을 대신하지 않는다. 이번 설명·점검 중 인스턴스
유형·JVM 설정·가드·시험 합격 판정은 변경하지 않았다.
