# 4GiB 공공데이터·동선 생성 245건 보완 검증 결과 (2026-09-07)

**판정: 이번에 선택한 기능과 요청량에서는 현재 4GiB 설정 유지 가능.**
축제 70건·관광지 70건·동선 생성 105건을 모두 정상 처리했다. 본 시험 210건의 응답시간
목표를 만족했고, OOM·비정상 재시작·지속적인 swap 활동·회복 실패가 없었다.
최저 가용 RAM은 약 1.00GiB(26.922%)였다. 이 자료에서 설정 변경이나 메모리 증설이
필요하다고 판단할 근거는 발견되지 않았다.

앞선 [1,855건 결과](api-load-ec2-4g-20260907-no-kto.md)에 이어 빠졌던 기능도 확인했다.
**서로 다른 시각에 53요청/분과 7요청/분으로 수행했으므로, 원래 60요청/분의
2,100건 혼합 부하를 한 번에 통과했다는 뜻은 아니다.** 4GiB에 부하가 전혀 없다는
뜻도 아니다. 이번에 측정한 부하를 여유를 남기고 처리했다는 판단이다.

## 메모리·CPU·GC와 요청 영향

480개 표본과 종료 표식을 모두 확보했고 수집기 exit code는 0이다.
실제 부하 시각 안의 표본은 418개다. 목표 간격은 5초이며 최대 간격은 6초였다.
01:23:00→01:23:06에 6초, 다음 01:23:06→01:23:10에 4초였고 나머지는 5초다.
표본 번호 0–479는 빠짐없이 존재한다. 시간 간격의 작은 변동을 표본 누락으로 세지 않았다.

| 항목 | 실제 부하 구간 |
|---|---|
| 최저 가용 RAM | **1,050,968KiB = 약 1.002GiB, 26.922%** |
| 가용 RAM 첫 → 마지막 표본 | 1,091,456 → 1,067,376KiB |
| 호스트 CPU 평균 / p95 / 최대 | **3.343% / 4.310% / 9.507%** |
| backend 메모리 첫 / 최대 / 마지막 | 353.70 / 371.13 / 370.91MiB |
| GH Docker 표시 메모리 | 첫·최대·마지막 1,727.49MiB |
| PostgreSQL 메모리 첫 / 최대 / 마지막 | 60.76 / 75.06 / 58.86MiB |
| swap 첫 / 최대 / 마지막 | 372 / 372 / 372KiB |
| 전체 관측 swap-in/out 증가 | 0 / 0 page |
| JVM/kernel OOM, 비정상 서비스 표본 | 모두 0 |
| backend/GH invocation·재시작 | 부하 구간 변경 없음 |
| GH·DB 컨테이너 restart / OOMKilled | 각각 0 / false |

CPU는 호스트 전체 counter 차분이다. backend 메모리는 systemd MemoryCurrent,
컨테이너 메모리는 Docker 표시값이며 서로 단순 합산하지 않는다. Docker 표시값의
같은 수치가 메모리 내부 변화까지 완전히 없었다는 뜻은 아니다.

부하 중 backend에서 일반 GC 1회가 발생했다.
01:47:29.469 UTC의 `Pause Young (Allocation Failure)`는 **7.857ms** 동안
heap **114→48MiB**를 회수했다. JVM OOM은 없었다. 전후 5초의 동선 생성 1건은
84.879ms·HTTP 200으로, GC 시작 약 53ms 전에 이미 응답을 마쳤다.
실제 부하 중 Full GC는 0회, GH GC 기록도 0회였다. GC 후 장기간 추세를 입증할
여러 표본이 없으므로 장기 누수가 없다는 증명으로 확대하지 않는다.

최장 요청은 01:48:09.332 UTC의 동선 생성 381.715ms였다. 위 GC 시각과 다르며
정상 응답이다. 부하 CPU 최대 9.507% 시각인 01:50:05 전후 5초의 요청 1건도
39.779ms로 정상 처리됐다. 메모리·swap 문제와 실패가 반복해서 함께 나타나지 않았다.

**계획된 종료 작업은 별도다.** 가드 OFF를 위한 backend 재기동 후
01:56:55에 CPU 97.473%가 관측됐다. 새 invocation의 시작 중 Full GC 4회
(24.486/72.775/49.283/101.461ms)가 기록됐으며 부하 종료 뒤의 Metadata GC Threshold다.
이를 정상 부하 구간의 CPU 최대·Full GC 횟수에 넣지 않았다.

## 공공데이터와 백업

가드가 확인한 실제 송신 52회는 모두 정상이다. unsafeEvents/non2xxResults/
malformedLines/counterGaps/overLimit는 모두 0이며 invocation·NRestarts도 유지됐다.

| 실제 외부 endpoint | 송신 |
|---|---:|
| KTO 축제 | 8 |
| KTO 국문 위치 기반 조회 | 14 |
| KTO 웰니스 위치 기반 조회 | 14 |
| KTO 두루누비 코스 | 2 |
| 카카오 카테고리 | 7 |
| 카카오 키워드 | 7 |

KTO 합계 **38회**, 카카오 합계 **14회**다. 서버 가드 사전 확인의 두루누비 2회·
축제 1회도 이 수에 포함되므로 부하 중 송신만의 수로 표시하지 않는다.
앱 요청 수보다 외부 송신이 적은 것은 정상 캐시 정책을 유지한 결과다.
이번 관측에서는 앞선 공공데이터 시간초과가 재현되지 않았다. 이를 전날 장애의
장비·정책 수준 근본 원인까지 규명한 것으로 바꾸지 않는다.

full backup 1회와 WAL 검사 3회 모두 실제 새 invocation으로 성공했다.
백업은 01:33:50.623–01:34:43.319 UTC, **52.696초**였고 그동안 송신한 앱 요청 4건이
모두 정상, 최대 **70.393ms**였다. WAL 검사는 01:27:10, 01:37:10, 01:47:10에
각각 0.276/0.293/0.276초 걸렸다. WAL 실행의 짧은 구간과 직접 겹친 앱 송신은
각 0건이며, 전체 부하 실행 중 수행했다는 사실과 구분한다.

## 복귀·검증·판단 범위

가드 OFF, backend 재기동·readiness, 공개 HTTPS 200, 정상 코스 동기화 true,
NTP 동기화 yes를 확인했다. 계측 service와 만료 복구 timer는 inactive다.
GH·DB 컨테이너는 기존 ID로 계속 실행되고 시험 전후 설정·SHA·graph도 동일하다.
제품 API·DB 스키마·Android 코드는 바꾸지 않았으며 계정 비밀값을 수집하지 않았다.
외부 운영자에게 문의·메일·댓글을 보내지 않았다.

새 실행기는 공통 요청·응답 검증기를 재사용하고 245건만 선택한다.
오프라인 `python -m unittest test_run_api_kto_supplement test_run_api_capacity test_run_api_load`
29개가 두 차례 통과했고 dry-run도 두 차례 같은 hash·건수를 냈다.
내용 실패 후 계속 실행, HTTP 500 보호 중단 시 미실행 보존, preflight 실패 시 부하 0건을 검증했다.
`git diff --check`도 통과했다. 제품 변경이 없어 backend/Android 빌드는 실행하지 않았다.

앞선 1,855건과 이번 245건 모두 성공했고 두 범위에서 4GiB의 메모리 부족 징후는 없었다.
따라서 **현재 4GiB를 유지**한다. 다만 원래 혼합 부하에서 모든 작업이 겹칠 때의 여유,
더 큰 입력·다른 캐시 상태·장기간 동작까지 합격했다고 확대하지 않는다.
8GiB 혼합 시험의 동선 생성 p95 421.563ms보다 이번 343.815ms가 짧지만,
동시 작업량이 다르므로 RAM 용량 때문에 빨라졌다고 해석하지 않는다.
