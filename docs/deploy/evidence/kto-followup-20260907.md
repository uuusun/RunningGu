# KTO 시간초과 재조사 — 2026-09-07

상태: **EC2·PC 연결과 조회 회복 확인. 같은 날 다른 기관 API의 무응답 신고도 확인했다.
공통 접속 구간의 일시적 문제라는 추론을 지지하지만 장비·정책 수준의 근본 원인은 미확정이다.**

사용자가 8GiB의 성공 기록과 비교해 원인을 더 조사하도록 요청했다.
[전날 진단](kto-tls-diagnosis-20260906.md)의 실패 기록은 보존한다.
현재의 성공을 전날 최초 실패의 원인 규명이나 부하 시험 합격으로 대체하지 않는다.

## 이번에 새로 확인한 사실

2026-09-07 06:51 KST(2026-09-06 21:51 UTC), PC에서 `apis.data.go.kr:443` 보안 연결이
성공했다. 키 교체·서버 설정 변경·보안 검증 해제 없이 TLS 1.3 연결이 맺어졌다.

| PC 진단 | 시작 시각 UTC | TCP까지 | TLS | 결과 |
|---|---|---:|---:|---|
| DNS를 분리한 TLS 입출력 관찰 | 21:51:03 | 44.023ms | 41.060ms | 정상 |
| 전날과 같은 기본 SSLContext, ALPN 설정 없음 | 21:51:54 | 131.209ms | 150.250ms | 정상 |
| HTTP/1.1 ALPN 제안만 추가 | 21:51:55 | 144.979ms | 59.580ms | 정상 |

첫 진단의 DNS는 55.812ms, 조회된 IPv4는 `27.101.236.63`으로 전날 PC 조회와 같다.
보안 연결에서 받은 바이트와 연결 완료를 확인했다. 세 경우 모두 TLS 1.3과
`TLS_AES_128_GCM_SHA256`을 협상했다. 현재 사용된 Python SSL 런타임은
`OpenSSL 3.5.8 25 Aug 2026`이다. 전날 PC 런타임 버전은 당시 증거에 없으므로 동일 버전이라고
소급 단정하지 않는다. 비교표의 두 번째·세 번째 TCP까지 시간에는 DNS 조회가 포함된다.

세 진단은 모두 **HTTP 요청 0회**이며 API 키를 읽거나 전송하지 않았다.
ALPN 유무 양쪽에서 성공해 이번 성공을 ALPN 변경 효과라고 해석하지 않는다.
첫 진단 JSON의 `tlsRecordsReceived`는 소켓 수신 청크 기록이며 TLS 레코드 경계를 분석한 것이
아니다. `firstRecordType`이라는 원래 필드명도 청크 첫 바이트를 뜻하므로 레코드 종류로 쓰지 않는다.

확정할 수 있는 변화는 **전날에는 TLS 응답이 관측되지 않았지만 이번에는 응답과 연결 완료가
관측됐다는 것**이다. 공급자가 무엇을 고쳤는지, 특정 장비·경로가 바뀌었는지는 이 자료에 없다.

## AWS 재로그인 뒤 EC2 진단

사용자가 AWS 로그인 완료를 알린 뒤 진단을 재개했다. 아래 UTC 날짜는 2026-09-06이며,
KST로는 **9월 7일 08시대**다.

| 관측 | UTC 시각 | 결과 |
|---|---|---|
| EC2 Python TLS | 23:01:52 | DNS 2.219ms, TCP 6.414ms, TLS 25.459ms, TLS 1.3 성공 |
| EC2 Java 21.0.12 TLS | 23:01:53 | TCP까지 22.330ms, TLS 195.786ms, TLS 1.3 성공 |
| EC2 두루누비 첫 페이지 1회 | 23:03:59 | TCP 26.159ms, TLS 24.501ms, 응답 헤더 178.422ms, 본문 39.532ms, 전체 273.133ms |
| 같은 요청 응답 | 위와 같음 | HTTP 200, `resultCode=0000`, `itemCount=100`, `totalCount=142`, 본문 184143bytes |
| 최종 상태 | 23:08:22 | 가드 OFF, backend active, 내부 contests 조회 200 |

EC2 TLS 진단 두 건은 HTTP 송신 없이 수행했다. 그 뒤 실제 조회는 최대 1회·재시도 0회로
첫 페이지에 한정했다. 제품과 같은 연결 제한 1초·읽기 제한 2.5초를 사용했고 HTTP redirect를
따르지 않았다. 키는 EC2 프로세스 환경에서 메모리로만 읽어 정식 HTTPS API에만 보냈다.
2,100건 부하 재실행이나 가드 초기화는 없었다. 내부 readiness 조회 1회는 공급자 호출과 별개다.

전날 사용한 Java 진단 소스를 그대로 재사용했다. SHA-256은
`59508303f9224412edc0a835e294585c3d5ad8cf4f15437fcbcfb4d7f23d83c9`다.
이번에도 Java 런타임은 `21.0.12`다. EC2 Python의 OpenSSL은 `3.0.13 30 Jan 2024`다.

서버에서 대조한 불변 항목:

- backend SHA·release: `673a2f796052f4553113d5cd25608fb3821222ac`.
- PID `356839`, InvocationID `44a631b7add84c63b46257c04cf2fe4d`, NRestarts `0`.
  전날 가드 해제 뒤의 동일 프로세스이며 이번 조사에서 재기동하지 않았다.
- backend Xms256m/Xmx512m, MemoryHigh 640MiB/MemoryMax 768MiB 유지.
- `application.env` 수정 시각: `2026-09-06T07:49:43.274215Z`로 전날 가드 해제 시각 이후 변경 없음.
- 실제 프로세스의 proxy·KTO URL/timeout·JAVA_TOOL_OPTIONS·JDK_JAVA_OPTIONS 관련 override 이름 없음.
- 최초 source 조회는 root로 실행해 SHA가 빈 값으로 수집됐다. 이를 유효한 SHA로 쓰지 않고,
  실행서대로 저장소 소유자인 `runninggu`로 재조회해 위 SHA와 exit 0을 확인했다. 원본 빈 값은 보존했다.

## 원인을 어디까지 확인했는가

**확정:** 전날 EC2·PC의 TLS 실패가 관측됐고, 현재는 같은 서버 프로세스·메모리 상한·Java와
같은 대상 IPv4에서 연결 및 데이터 조회가 성공한다. 이번 진단에서 재배포·재기동·timeout 조정·
보안 검증 해제 없이 성공했다. RAM 증설이나 키 교체로 이 현상을 해결해야 한다는 근거는 없다.

**미확정:** 외부 게이트웨이가 왜 TLS 응답을 보내지 못했는지, 특정 연결 처리 장비나 통신 경로가
무슨 상태였는지는 우리 쪽에 원인 기록이 없다. 최초 16:47 사건은 가드가 원래 I/O 예외를
보존하지 않아 TLS 실패였다고 소급 확정할 수도 없다. 따라서 “일시적으로 응답하지 않았다”는
관측을 장비·정책 수준의 근본 원인 규명으로 보고하지 않는다.

장비 내부의 원인을 더 구분하려면 공급자 운영팀의 해당 시각 로그가 필요하다.
시각·경로·측정값·확인 질문을 정리했던 문의 초안은 로컬 참고 자료로 보존하고 저장소에는 올리지 않는다.
인스턴스 ID·비밀값·계정 정보는 문의 초안에 포함하지 않았다.
**사용자가 외부 문의를 남기지 말라고 지시했으므로 문의 등록·메일 발송을 하지 않는다.**
초안은 로컬 참고 자료로만 남기며, 공개 게시판에서는 기존 글 세 건만 읽었다.
새 문의 등록·메일 발송·좋아요·댓글·공유는 모두 수행하지 않았다.
공식 문의 경로는 [공공데이터포털 문의하기](https://www.data.go.kr/bbs/faq/selectFaqList.do)이며,
운영자 메일·대표전화도 공식 사이트 푸터에서 확인했다.
