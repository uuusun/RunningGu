# KTO 두루누비 시간초과 후속 진단 — 2026-09-06

후속: [9월 7일 재조사](kto-followup-20260907.md)에서 EC2·PC TLS 및 두루누비 조회 회복과
다른 기관 API의 같은 날 무응답 신고를 확인했다. 아래는 9월 6일 실패 당시 관측이며,
장비·정책 수준의 원인까지 확인된 것은 아니다. 사용자 지시에 따라 외부 문의는 하지 않는다.

**재현한 실패 구간은 `apis.data.go.kr:443`의 TLS 연결 협상이다.** DNS 조회와 TCP 연결은
성공했지만 HTTPS 암호화 연결을 시작하는 ClientHello에 TLS 응답이 오지 않았다.
EC2와 PC, Python과 서버 Java 21, TLS 1.2와 1.3에서 재현됐다. 같은 시각 비교한 다른
HTTPS 호스트에서는 TLS 연결이 성공했다. 현재 조치 대상은 해당 API 게이트웨이와 그 앞의
TLS 종료·접근 제어 경로다. 어느 장비 또는 정책이 응답을 막는지는 공급자 측 로그가 필요하다.

이 문서는 [v3 부하 시작 전 실패](api-load-ec2-4g-20260906-v3.md)의 **후속 원인 조사**다.
새 부하 run을 시작하거나 기존 가드를 초기화하지 않았다. 최초 07:47 UTC 실패의 상세 원인과
08:20 이후 직접 재현한 TLS 실패를 구분한다. 모든 표의 날짜는 2026-09-06이다.

EC2에서 실패한 두 소켓을 각각 로컬 포트로 한정해 `ss -tin`으로 확인했다.
TLS 1.2는 `bytes_sent=212`, `bytes_acked=213`, TLS 1.3은 각각 `249`, `250`이었다.
TCP 확인 번호에는 연결 수립에 쓰인 번호가 포함될 수 있으므로 1바이트 차이를 추가 응답으로
해석하지 않는다. 두 소켓 모두 송신 데이터 세그먼트 1개에 대해 수신 확인이 왔고,
수신 데이터의 `bytes_received`·`data_segs_in` 필드는 표시되지 않았다.
즉 **상대 TCP 종단 또는 중간 프록시가 ClientHello 바이트를 확인했지만 TLS 응답 데이터는
관측되지 않았다.** `retrans`·`lost`도 표시되지 않았으나 이를 전체 경로의 손실 0 증명으로 쓰지 않는다.

08:29:03 PC DNS 조회에서 IPv4 `27.101.236.63`과 합성 IPv6 주소가 나왔다.
PC Python 진단은 IPv4를 선택했으며 IPv6 주소로 접속한 결과가 아니다.

## 최초 실패와의 관계

배포 SHA `673a2f796052f4553113d5cd25608fb3821222ac`의 KTO 설정은
`https://apis.data.go.kr/B551011/Durunubi`, 연결 제한 `1s`, 읽기 제한 `2500ms`다.
서버 환경에 이 세 설정을 바꾸는 override는 없었고 서비스 키는 존재했다. 키 값은 수집하지 않았다.

성공 기록은 모두 `bundleCount=261`, `ktoCount=142`, `matched=140`, `gpxOnly=121`,
`apiOnly=2`, `invalidFields=0`이다. 따라서 계속 잘못된 키나 고정된 연결 차단만으로 이번
현상을 설명할 수 없다. 다만 성공/실패 시점 사이에 응답 상태가 달라졌다는 사실만 확인했으며,
공급자가 장애 복구를 했거나 특정 정책을 바꿨다고 추정해 사실로 적지 않는다.

최초 실패의 stack은 `UpstreamLoadGuardInterceptor.intercept:54` →
`UpstreamLoadGuard.recordTimeout:143`을 가리킨다. 이 경로는 응답 본문 처리 전이다.
가드는 원래 I/O 예외의 cause를 보존하지 않고 `TIMEOUT_SIGNAL` 예외로 바꾸므로,
**07:47 실패 자체가 TLS였다고 소급 확정할 수는 없다.** 2707ms라는 지속시간과 후속 TLS
재현은 같은 종류의 문제라는 추론을 지지하지만, 최초 사건의 TCP/TLS 패킷 기록은 없다.

또한 가드 counter는 네트워크 실행 전 `reserve`에서 증가한다.
기존 보고의 “실제 외부 송신 1건”은 **가드가 허용한 호출 시도 1건**으로 정정한다.
그 counter만으로 HTTP 요청이 KTO에 도착했거나 KTO가 처리했다는 사실을 증명할 수 없다.

## 조치와 판단 범위

1. **공공데이터 API 게이트웨이 운영 측에 TLS 구간 점검을 요청할 근거가 확보됐다.**
   아래 전달문으로 해당 시각의 TLS 종료 장비·로드밸런서·접근 제어 장비에서 ClientHello 수신,
   응답 생성/전달, 연결 제한·차단 기록을 확인하면 장비와 정책 수준의 원인을 확정할 수 있다.
   이 조사에서는 외부 운영자에게 메시지를 보내지 않았다.
2. 현재 재현은 API 키 인증·두루누비 HTTP 처리·응답 본문 수신 이전에 실패한다.
   EC2 RAM 증설, 키 교체, 애플리케이션 재배포를 해결책으로 선택할 근거가 없다.
   TLS 1.2도 실패했으므로 버전 하향을 해결책으로 채택하지 않는다. 제품 timeout도 유지했다.
3. 08:27:41 UTC 최종 확인에서 가드 OFF, backend `active`, `NRestarts=0`,
   InvocationID `44a631b7add84c63b46257c04cf2fe4d`로 조사 전과 같았다.
   이 후속 진단 중 서비스 재기동·가드 변경·힙 변경·DB 변경은 없었다.
4. 4GiB 용량 판정은 계속 보류다. 앱 예정 부하 2100건은 전부 미실행이다.
   향후 별도 부하 실행은 외부 연결 정상화와 기존 가드 사전 점검의 성공이 먼저다.
   이번 원인 조사에서 재시험하거나 새 관찰 기간을 추가하지 않았다.

`apis.data.go.kr`을 게이트웨이 방식 API 인증 서버로 설명하는
