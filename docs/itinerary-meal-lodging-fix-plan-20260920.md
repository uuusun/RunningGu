# 동선 추천 수정 계획 — 식사 적합성·숙소 미선택

> 작성일: 2026-09-20 (KST)
> 상태: **명세·구현·로컬 자동 검증 완료. 운영 배포와 실기기 연동 확인 전.**
> 분석 기준: `811a45f02e9c533bc003f8b13bea1d86d59f56e1`, Android 후보 `1.0.2 (versionCode 3)`
> 이 문서의 권고안은 `SPEC.md` 결정-75로 확정한다. 운영 배포는 별도 릴리스 검증 뒤 진행한다.

## 1. 문제와 목표

사용자가 운영 서버에 연결된 APK를 확인하며 다음 두 문제를 제보했다.

1. 대회 전날 저녁 식사로 맥주집이 추천된다.
2. **‘숙소 없이 추천받기’**를 선택했는데 동선에 숙소 체크인이 들어간다.

목표는 **식사 목적에 맞는 후보만 자동 추천하고, 숙소 선택 여부를 일정 생성에 반영하는 것**이다.
빈자리를 채우기 위해 제외 대상 업소를 되살리거나 선택하지 않은 숙소 일정을 만들지 않는다.

제보된 맥주집의 정확한 업체명·원천 응답·업종 분류는 아직 확보하지 않았다.
아래 원인은 코드에서 확인한 허용 경로이며, 특정 업소가 어떤 원천과 분류로 들어왔는지까지 재현한 결과는 아니다.

## 2. 코드와 기존 명세에서 확인한 원인

| 항목 | 현재 동작 | 문제 |
|---|---|---|
| 식사 후보 필터 | `ItineraryGenerator.Picker.isMeal()`은 `음식점 > 간식`, `음식점 > 패스트푸드`만 제외 | 주류 중심 업소를 제외하는 규칙이 없음 |
| 식사 후보 부족 | `pickMeal()`은 필터 결과에서 고르지 못하면 원래 FOOD 풀에서 다시 선택 | 같은 필터에 주점을 추가하는 것만으로는 재등장을 막지 못함 |
| 업종 정보 | 카카오 `category_name`을 `description`에 담아 판정. KTO FOOD의 `description`은 빈 문자열 | `isMeal()`이 빈 설명을 적합으로 취급하므로 원천에 따라 검사가 우회됨 |

## 3. 확정한 수정 정책

### 3.1 자동 식사 추천

추천 순서는 **후보 분류 → 제외 규칙 적용 → 기존 거리·사용 이력 기준 선택**으로 둔다.
랜덤 선택과 후보 부족 처리는 제외 규칙을 통과한 집합 안에서만 수행한다.

| 분류 | 제안 동작 | 후보 부족 시 |
|---|---|---|
| 일반 식사 업소 | 자동 식사 추천의 우선 후보 | 기존 선택 규칙 적용 |
| 간식·패스트푸드 | 기존 결정-65의 후순위 후보 | 일반 식사 후보가 없으면 허용하되 주류 중심 업소는 제외 |
| 주류 중심 업소 | 주점·호프·바 등으로 확인된 업소는 모든 자동 식사 블록에서 제외 | 절대 다시 허용하지 않음 |
| 업종 미확인 | ‘적합’과 구분하는 내부 상태로 유지 | 확인되지 않은 후보를 자동 식사 추천에 넣지 않음 |

- 대회 전날 저녁뿐 아니라 점심·당일 저녁·회복 저녁에도 같은 제외 규칙을 적용한다.
- 일반 음식점에서 술을 판매한다는 이유만으로 제외하지 않는다. 업종의 주된 성격을 기준으로 한다.
- 업체명에 ‘맥주’가 들어가는지만 검사하는 방식은 주 판정 기준으로 사용하지 않는다. 실제 원천 분류를 확인한 뒤 분류 경로를 정규화해 판정한다.
- 카카오 분류와 KTO 분류를 서버 내부에서 공통 판정으로 변환한다. 사용자용 `description`의 표시 문구를 업종 판정 계약으로 사용하지 않는다.
- KTO 분류 코드나 누락 의미를 임의로 정하지 않는다. 실제 응답과 해당 원천 계약에서 사용할 수 있는 필드를 확인한다. 정보가 없으면 미확인 상태를 보존한다.
- PR #382 리뷰 반영으로 FOOD 조회 상한을 8건에서 15건으로 개정한다. 카카오 한 페이지 범위에서 후보를 더 확보하고, 분류 후 일반 식당 우선·후순위 순으로 최대 8건을 유지한다. 같은 등급 안의 거리순과 다른 카테고리의 8건 상한은 유지한다. 반경·원천 보충·캐시 정책은 그대로이며, 요청 수가 커져 기존 보충 조건이 더 자주 충족될 수 있다. 15건 밖의 후보 누락은 이 변경으로 완전히 해소되지 않는다.

### 3.2 식사 후보가 없을 때

- 식사 블록은 유지하고 기존 응답 형식의 장소 필드(`placeName`, `address`, `lat`, `lng`)를 null로 반환한다.
- 성공 반환된 조회 결과에 적격 후보가 없으면 설명은 **“추천할 식당을 찾지 못했어요. 편집에서 장소를 추가해 보세요.”**로 한다. 일부 원천이 실패해도 다른 원천 결과를 받았다면 이 안내를 사용한다. 모든 원천이 정상 응답했다는 뜻은 아니다(PR #382 리뷰 반영).
- 외부 조회 실패는 정상 0건과 구분한다. 장애 때는 **“식당 정보를 불러오지 못했어요.”**와 같이 원인을 단정하지 않는 설명을 사용한다. 최종 문구는 API 명세와 함께 확정한다.
- 장소 미정 블록에 지도 핀을 만들거나 방문 장소 수를 늘리지 않는다. 생성·저장·재조회·편집에서 null 장소를 일관되게 처리하는지 확인한다.
- 특정 식당의 메뉴를 검증하지 않은 상태에서 ‘소화 잘 되는 회복식’이라고 단정하지 않는다. 식당이 선택되면 **‘방문 전 메뉴와 영업시간을 확인해 주세요.’**로 안내해 제목 중복을 없애고, 검증되지 않은 이동 절감도 주장하지 않는다(PR #382 리뷰 반영).
- 사용자가 직접 장소를 추가·교체하는 기존 기능의 허용 범위는 이번 자동 추천 정책과 별개로 유지한다.

### 3.3 숙소 미선택

- `hotel == null`이면 **자동 생성되는 LODGING 블록은 전체 일정에서 0개**로 한다. 체크인과 체크아웃 모두 포함한다.
- 생성기는 숙소 블록을 추가하기 전에 숙소 존재 여부를 확인한다. Android가 응답을 받은 뒤 숨기는 방식으로 처리하지 않는다.
- 남은 식사·취향 후보 조회는 기존 대회장 중심 규칙을 유지한다.
- 숙소 블록을 뺀 자리를 다른 관광 블록으로 채우지 않는다.
- 숙소 선택 후 해제한 경우에도 미선택과 같은 결과를 보장한다. 미선택은 ‘숙박하지 않는다’는 뜻으로 확대 해석하지 않는다.
- 숙소가 있는 경우의 기존 날짜별 배치 규칙은 우선 유지한다. 다만 현재 D-2·D-1마다 체크인이 반복되는 문제와 D-day 시작·종료 여행의 체크인/아웃 시점은 별도 정책 검토 대상으로 기록한다. 이 수정만으로 숙박 일정 전체가 해결됐다고 보고하지 않는다.

### 3.4 저장된 동선

- 새 정책은 **새로 생성하거나 사용자가 재생성하는 동선**부터 적용한다.
- 이미 저장한 동선은 사용자 편집을 포함하는 snapshot이므로 자동 삭제·수정하지 않는다.
- 재생성 후 저장은 기존 교체 계약을 따른다. 서버 배포만으로 과거 저장본이 달라지지 않는다는 점을 검증 기록에 명시한다.

## 5. 구현 범위와 순서

| 순서 | 작업 | 주된 대상 |
|---|---|---|
| 1 | 원천 분류 필드를 확인하고 §4 정책을 확정·문서화 | SPEC, API 명세, 화면/API 매핑표 |
| 2 | 식사 적합성에 필요한 원천 분류를 서버 내부에 보존하고 순수 판정 로직 구성 | `poi/infrastructure`, 필요한 내부 POI 모델, `ItineraryPoiPoolLoader`, `ItineraryPlace` |
| 3 | 강제 제외가 모든 선택·폴백 경로에 적용되도록 식사 후보 선택 수정 | `ItineraryGenerator.Picker` |
| 4 | 숙소 존재 조건을 체크인·체크아웃 생성에 적용 | `ItineraryGenerator.generate()` |
| 5 | null 장소 안내와 생성·저장·조회 계약 확인 | 생성 응답, 저장 서비스, Android 매퍼·결과 화면 |
| 6 | 회귀 테스트와 APK 연동 확인 후 배포 기록 작성 | 백엔드 테스트, Android 관련 테스트, 릴리스 검증 기록 |

- 엔진은 기존처럼 서버 단독 생성 주체로 유지한다. 사용하지 않는 Android `ItineraryEngine`을 운영 경로에 연결하지 않는다.
- 공개 API 필드 추가·DB 스키마 변경·새 라이브러리 없이 처리하는 것을 우선한다. 필요성이 생기면 계약부터 별도로 검토한다.
- 거리 최적화, 방문 수 재설계, 메뉴·영양 추론, 추천 모델 도입은 이 수정 범위에 포함하지 않는다.
- Android 수정이 필요하면 앱 코어·UI 담당과 연결부 계약을 확인한다. 기존 null 장소 표시로 요구를 충족하면 서버 수정으로 해결한다.

## 6. 검증 계획

아래는 **실행 예정인 검증**이며 통과 결과가 아니다.

| 사례 | 입력·조건 | 기대 결과 |
|---|---|---|
| 식사 1 | 일반 식당과 주점이 함께 존재 | 자동 식사 블록에 주점이 한 번도 나오지 않음 |
| 식사 2 | 주류 중심 업소만 존재 | 장소 미정 식사 블록, 주점으로 폴백하지 않음 |
| 식사 3 | 패스트푸드와 주점만 존재 | 후순위 허용 정책에 따라 패스트푸드 선택, 주점 제외 유지 |
| 식사 4 | 일반 음식점이 술도 판매 | 주류 판매 사실만으로 제외하지 않음 |
| 식사 5 | 분류 누락·빈 설명·KTO 폴백 | 합의한 미확인 정책 적용, 누락을 적합으로 자동 해석하지 않음 |
| 식사 6 | 원천 분류의 공백·계층 차이 | 정규화한 업종 판정이 일관되며 표시용 설명 변경에 영향받지 않음 |
| 식사 7 | 일반 후보 소진·같은 조건 재생성 | 반복 선택·랜덤 선택·폴백 경로에서도 주류 업소 제외 유지 |

## 7. 운영 반영과 완료 기준

운영 서버가 한 대이므로 먼저 로컬 테스트와 테스트 DB로 생성·저장·조회 회귀를 검증한다.
APK 연동은 로컬 백엔드 연결용 테스트 빌드로 검증할 수 있다. 운영용 APK는 운영 주소를 유지한다.
스테이징 서버가 다시 생겼다고 가정하지 않는다.

배포 단계에서는 변경 커밋과 검증 산출물을 고정하고, 직전 운영 산출물·설정 및 복구 절차를 확인한 뒤
신규 생성 요청으로 두 제보 사례를 점검한다. 운영 환경의 저장 검증은 지정된 테스트 계정·데이터 범위에서 수행한다.
이번 수정에 DB 마이그레이션이 없다면 장애 시 직전 서버 산출물로 복귀할 수 있지만,
롤백이 저장된 snapshot을 자동 복구·변경하는 것은 아니다.

- 서버가 기존 응답 형식으로 해결하면 현재 APK도 새 생성 결과를 받을 수 있다. 실제 연동 확인 후 확정한다.
- 앱 수정이 필요하면 APK를 재빌드한다. 스토어 업데이트 후보의 버전 코드는 그 시점에 등록된 최대값보다 높게 정한다.
- 사용자 확인과 남은 QA를 거친 뒤 기존에 합의한 릴리스 PR·main·태그·스토어 출시 절차로 이어간다.

## 8. 구현 및 검증 결과

### 반영 결과

- 공개 API 필드와 DB 스키마는 바꾸지 않았다. 카카오 `category_name`과 KTO `lclsSystm2`는 서버 내부
  `Poi.sourceCategory`에만 보존하고, `MealSuitability`로 변환한 뒤 생성기가 소비한다.
- 일반 식당이 없을 때만 후순위 후보를 사용한다. 주류 중심·분류 미확인 후보는 후보 소진과 재사용
  경로에서도 선택하지 않는다.
- `hotel=null`이면 D-1 체크인과 마지막 날 체크아웃을 모두 생략한다. 다른 블록을 추가해 자리를
  보충하지 않는다.
- 적격 식당 0건과 외부 조회 실패는 기존 nullable 장소 응답을 유지하면서 설명으로 구분한다.
- Android 코드는 바꾸지 않았다. 기존 매퍼는 장소 null 블록을 유지하고, 지도 상태는 좌표가 있는
  블록만 핀으로 만든다.
